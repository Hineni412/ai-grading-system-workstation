## 本次直接处理与系统 API 生成的区别

最近的 HTML 排版、统计和导出确实调用项目共用程序。AI 分析内容由当前对话生成并准备好，再交给程序使用。因此，它不是“同一个模型、同一份输入、相同推理设置、点击系统生成”的严格对照。

| 环节 | 本次实际做法 | 普通配置 API 是否已有 |
|---|---|---|
| 资料准备 | 读取评分规则、教师最终分、原题、作答图，必要时查看整页 | 共用程序已经支持图文资料，但题框外作答仍可能漏在局部图外 |
| 阅卷及错因分析 | 当前对话模型看卷，遇到不确定处补看图、对照规则，区分空白、错误、步骤缺失 | 系统有判分规则、图文报告提示词；并不自动获得本次对话中的全部补充核查 |
| 模型条件 | 当前对话使用 GPT-6 Astra；最早 4 份系统 API 样本使用豆包 | 模型和工作方式都不同，不能单独归因于某一个因素 |
| 共用问题修复 | 发现单位、空白、统计、题图和渲染问题后改代码，测试后重跑 | 已修代码会用于后续生成；修改代码本身不是每批正常业务都要付出的成本 |
| 成品检查 | 核对报告人数、成绩、小问覆盖、题图、公式及电脑和手机布局 | 本次做过的完整检查还没有全部变成系统导出流程 |
| 新评分疑点处理 | 保留教师最终分并提示核对；本次另外整理入口 | 系统还缺少集中处理、记录决定及导出前收口的闭环 |

质量提升有可解释的来源：模型条件不同、输入证据更完整、较多上下文和多次核查，以及发现共用缺陷后重新生成。但目前没有受控对照，不能给出“质量提高百分之多少”，也不能保证配上相同模型就完全复现本次结果。

建议将稳定的检查做成普通程序：人数与成绩一致、小问无遗漏、图片和公式可用；把需要判断的少数冲突集中交给教师。开发阶段的代码修复和反复排版检查不必每批重新进行。此处是建议，尚未实施。

## Token 用量：实际可核对的记录

Token 是模型处理文字、图片等内容时使用的计量单位。此次有两条独立用量来源：项目模型 API，以及 Codex 对话模型。纯 Python 计算、读取数据库、渲染 HTML 本身不调用模型；让代理阅读工具输出、分析、写代码和检查结果，则会消耗对话模型 Token。

按请求的实际用量累加并检查请求不重复。输入总量已经包含缓存输入；输出总量已经包含推理输出，不能将这些子项再加一遍。字段含义参见 [OpenAI Responses 官方用量定义](https://developers.openai.com/api/reference/typescript/resources/beta/subresources/responses/methods/create)。缓存是重复输入被复用，不等于这部分完全没有资源成本；这里不按模型价格推算金额，也不将不同服务的 Token 当作相同价格。
