# 七项实现复核与八上优化方向

日期：2026-10-15。用途：保留七项改进的适用范围复核，以及本轮实现前的八上调查依据。当时的隔离实验只在测量进程中临时替换函数；后续代码实现与验收见[八上读取优化与验证](backend-g8-upper-performance-implementation-20261015.md)。下文耗时属于调查时的样本。

## 七项改进是否只针对空学期

七项改进主要位于通用读取路径，八上同样使用。没有为七上、七下、八下、九上建立各自的读取实现。上轮以四册空范围集中验收，是为了复现当时的主要症状，不能据此推断八上所有页面已经达标。

| 已实现项目 | 生效条件与八上影响 |
|---|---|
| 空考试提前返回 | 任意学期的所选考试范围为空时生效；当前八上全部学生、三场考试的读取不走此分支 |
| 省去不显示的资料 | 按完整、摘要、显示模式及目标类型生效，八上显示诊断同样受益 |
| 按需加载试卷分析状态 | 全部试卷目录共用，八上目录也先显示元数据 |
| 复用有效显示结果 | 各学期与范围共用；返回已查看且未失效范围时受益 |
| 轻量候选筛选 | 所有候选请求共用，包含八上；上轮尚未测出稳定的大幅冷读收益 |
| 按册和来源缩小失效 | 按实际册别、题目和共享标准生效，八上本册缓存同样受保护 |
| 合并评价和摘要读取 | 全部考试共用，已有八上试卷评价对照 |

下一轮应以八上的真实使用流程作为主要验收样本，继续改通用实现。这样新增其他册的数据后也能受益，无需增加八上专用分支。

## 对上轮交付的判断

已读取任务“实现七项读取优化并对比验证”的完成结果，核对其调查报告、关键实现、计时和页面记录。上轮报告明确保留了未达标项：五个空范围页面首次仍需约 1.39–1.97 秒，候选冷读仍约 5–10 秒，章节缓存新进程命中多约 33 毫秒。因此“七项代码均已实现”应理解为实现范围完成，不能理解为所有性能目标完成。

上轮已有后端 114 个用例、前端和编辑器合计 16 个用例的通过记录。本轮没有重新运行整套回归，也没有改业务代码；重点是补齐上轮缺少的八上显示诊断、学情测量，并定位剩余成本。

## 八上补测

范围：全部 91 名学生、八上三场关联考试。首次禁用派生结果磁盘缓存，每次独立进程；保留操作系统文件缓存，预先导入和进程启动不计时。测量包含原有请求读取上下文；不包含浏览器渲染和 HTTP 排队。

对照使用上轮修改前的源码快照与当前源码，两端读取同一份真实输入。只读保护禁止真实写入与网络，源数据库状态检查全部通过，临时数据库副本已回收。输出只记录耗时、数量及完整结果摘要，不保存学生或题目正文。

### 显示诊断的交替对照

各执行两次，顺序为“前、后、实验；实验、后、前”。下表是两次样本的中位数，单位为秒。小样本仅用于判断方向，不代表长期百分位。

| 路径 | 首次读取 | 同进程命中 |
|---|---:|---:|
| 七项修改前 | 6.592 | 0.102 |
| 七项修改后 | 6.057 | 0.100 |
| 仅测量进程：先取显示字段，再整理输出 | 4.826 | 0.096 |

三种方式的完整返回摘要一致。七项修改对这条路径的样本收益约 8.1%；显示字段顺序实验相对当前实现约减少 20.3%。实验保留当前输入的非有限数检查与显示契约；尚未验证全部异常输入、分组响应及其他调用者，不能直接视作正式修复通过。

初次未交替样本曾测得 10.269 秒，后续当前实现的两次样本为 5.976、6.137 秒。不能把初次较慢值作为稳定基准，也不能据此断定回归。剖析自身也有开销，下面只把它用于识别耗时位置。

八上学情概览另做单次同输入对照：4.134 → 3.897 秒，完整结果一致；当前同进程命中约 0.044 秒。这组样本不足以判定稳定收益。

独立进程允许读取现有磁盘条目时，显示诊断为 5.272 秒、概览为 2.850 秒。两者各命中一个基础条目，仍需组装最终结果；这些不是完整结果的磁盘命中性能。

## 下一轮优先项

### 1．减少出训练显示结果的重复加工

已定位：`backend/api/routers/training.py::_diagnosis_response_bytes` 先对摘要诊断执行 `_public_training_mapping`，然后 `_validated_diagnosis_json` 才裁出显示字段。一次八上剖析中，前一阶段递归访问约 84 万次，累计约 2.900 秒；这是剖析样本，不能作为直接可节省的固定时间。

八上响应有 41,029 个学生与知识项组合。它们包含未观测和证据不足项，不是 41,029 个实际薄弱点。建议先确定显示响应所需字段，再整理、校验和序列化；保留所有现有数值、顺序、来源数量和共享目录。隔离实验已经证明该输入下可进一步降至约 4.83 秒。

### 2．让原题判重真正复用已计算身份

已定位：候选加载虽然不再准备完整图片载荷，但 `question_identities` 仍调用 `exam_original_key`。该函数在读取缓存的公式摘要前，先打开富文本正文并整理公式输入。一次来源有效候选剖析出现 499 次原题身份计算、999 次正文加载调用和 499 次正文解析。

这解释了轻量候选改造为何没有明显缩短首次读取：后面的判重路径重新引入了正文成本。建议复用现有身份缓存和题目版本，保存并直接读取整题原题身份；只为缺失或确已变化的题目补算。这里的去重标识仍有业务用途，应保留，不能通过取消排除原题来换速度。

### 3．精简掌握度结果组装与缓存标识准备

已定位：一次显示诊断剖析中，`semester_mastery` 累计约 3.317 秒，包含掌握度计算约 2.535 秒；`_merge_current_mastery` 另约 1.093 秒。模型拟合 `fit` 自身约 0.585 秒，说明应先处理外围结果加工，而不是先改变统计模型。

`cache_values(calculation_profile)` 仍会遍历整份观测生成内存缓存键，剖析约 0.501 秒。它没有计算内容哈希，但仍有全量遍历成本。建议使用已知的考试、材料、训练版本、范围、时间和参数构成小型标识，并复用统一目录与父子关系索引。保留原群体拟合范围、先验、未观测项和所有输出，不能删学生或改评分口径。

这些耗时存在嵌套，不能相加为整体耗时，也不能据此承诺最终低于一秒。

### 4．试卷评价只准备实际涉及的章节统计

已定位：`backend/reporting/paper_review.py::_coverage_materials` 为涉及的册调用完整章节考情，再取其中的相关节。一次评价剖析中调用了两次 `chapter_exam_profile`，累计约 3.016 秒。

建议把现有章节统计读取限定到评价实际涉及的章节，并复用已读的材料和难度。原典型题、难度分布、覆盖度、跨册知识、六维评价及教师最终分语义继续保留。不要只把耗时转移到后台并宣称冷读已经优化。

### 5．最后处理整页启动与小幅缓存开销

上轮浏览器记录显示，空范围页面导航后约 0.6–0.9 秒才发首批资料请求，随后再发业务请求。该启动链也是通用的，但本轮没有测八上浏览器完整页面，不能直接套用这些数字。

建议在八上后端主要耗时减少后，检查教材目录、考试列表与当前页读取能否并行，并测按班切换、小组诊断、生成前读取及缓存失效后的刷新。章节缓存额外约 33 毫秒也应保留对照，但优先级低于当前数秒的冷读。
