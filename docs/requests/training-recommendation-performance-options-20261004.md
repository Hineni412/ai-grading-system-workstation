# 训练推荐后端：成熟优化方法调查

用途：回答“目前仍要几十秒，是否有更成熟的优化方案，开源项目有哪些可借鉴做法”。本文用于方案讨论，不是实施记录或性能承诺。业务规则以 [题库、组卷与个性化训练](../product/KNOWLEDGE_AND_TRAINING.md) 为准；本地测量口径见 [后端性能交接](training-recommendation-backend-handoff-20261004.md)。调查日期：2026-10-04。

快速浏览：[方案图](training-recommendation-performance-options-20261004.html)。本 Markdown 是详细调查，方案图只用于说明。

状态：E 的计算优化已实施，实际机制与测量统一记录在[后端性能交接](training-recommendation-backend-handoff-20261004.md)。当前使用现有投影、紧凑评分输入、内部只读共享、请求内统计与进程内内容缓存。Numba、位集合库、新的持久派生存储与精确变更记录仍是未实施的备选。本轮没有安装新依赖、写真实数据库或调用模型。没有找到可以保持本项目逐项结果、直接替换现有推荐引擎的通用开源项目。

## 1. 推荐结论

建议采用“识别实际计算依赖，复用未变的中间结果，减少冷计算中的 Python 对象处理”这一组合。已有缓存和预热继续使用。重点从请求内复用推进到跨请求的内容复用，并改善真正需要重新计算时的耗时。

这包含三个相互配合的工作：

1. 把一次推荐拆成有明确输入的计算步骤。数据提交后先检测变化，再核对这些步骤的实际输入。输入未变的步骤复用原结果；输入变化的步骤完整重算。
2. 把题目、来源证据和掌握度的重复读取整理成可复用的只读计算资料。内部共享不可修改的资料，最终输出时按原规则组装独立对象。
3. 把“学生 × 技能 × 候选”的字典循环和分组试卷检查改为紧凑的数组、索引和集合运算。保留原排序、边界判断和选题顺序。

Bazel、SQLite、joblib、DiskCache、Numba 和 RoaringBitmap 提供了相关方法或组件。优先借鉴它们已明确的行为，再决定是否引入库。当前规模和运行方式不足以支持“先加 Redis、Celery 或向量数据库就能解决”的结论。

## 2. 当前证据与边界

已核实的本地现状：

- 现有实现已经缓存完整诊断响应、分组、掌握度和候选资料，并有空闲预热。完整诊断及分组响应还可保存到本地快照。不能把后续方案写成“从零增加缓存”。见 [ARCHITECTURE.md](../../ARCHITECTURE.md) 的知识训练缓存说明。
- `integration/result_cache.py` 已有同一缓存键的并发请求共用一次计算。`personalized.py` 的候选缓存使用该组件，来源键仍包含整库提交代次。后续重点是提交后识别实际依赖，不能去掉变化检测。
- 计算前后配对及首章完整页面已分别测量，口径与结果见交接文档。候选缓存命中后重新分组与完整响应缓存命中是不同场景；不能把后者约一秒的页面等待当作首次或更新后的耗时。
- 已重新记录热点，并据此减少深拷贝、固定偏好计算和选卷重复统计。当前仍有候选正文与图片核对、来源签名及逐生选题循环，不能仅凭复用模式承诺首次页面两秒。
- 当前掌握度模型先用学期全体学生的观测拟合群体参数，再取得请求范围。单个学生新增有效观测，也可能改变其他学生的掌握度。不能承诺只重算该学生。

保持的产品条件：同一输入下，题目、题序、用途、推荐理由、警告、分组成员、卡片统计和来源版本逐项不变；页面仍一次收到完整诊断及小组结果；发现相关输入变化后必须刷新，不返回已知过期结果。

## 3. 最有价值的做法：按内容拆分计算

成熟依据：Bazel 的 Skyframe 把计算组织成不可修改的节点和依赖关系。输入变化后，只重建依赖这些输入的节点；如果重建后的中间值与原值相同，后续节点可以恢复复用。它同时强调，未登记的读取会破坏增量计算的正确性。[Bazel Skyframe 官方文档](https://bazel.build/reference/skyframe)

本项目建议借鉴这个原理，不把 Bazel 当作运行时推荐组件，也不先建通用计算框架。先给现有热点函数明确输入和结果：

| 可拆分的计算资料 | 实际依赖必须包括 | 可独立复用的内容 |
|---|---|---|
| 题目计算资料 | 当前判定版本、技能与知识关联、题面、图片身份、难度特征、资料校验规则 | 标签集合、匹配所需信息、难度与正文特征 |
| 冻结来源小问资料 | 考试或训练的稳定标识、修订、冻结正文与关联、相关解析版本 | 来源标签、作答方式、难度特征 |
| 掌握度计算 | 学期全体有效观测、群体模型参数、自然周、排除证据、知识版本 | 全体模型结果及按学生索引 |
| 目标与候选匹配 | 目标内容、候选计算资料、知识标准与匹配规则 | 匹配等级与资格结果 |
| 来源与候选偏好 | 来源计算资料、候选计算资料、偏好规则 | 不依赖学生动态状态的固定偏好 |
| 逐生候选评价 | 当前掌握度、需要、候选资格、近期原题、全部出卷设置 | 适合难度、用途与候选排序统计 |
| 自动分组 | 全体成员输入、候选评价、分组规则与设置 | 最终分组及每次试卷选择结果 |

这是依赖清单的起点。实施前还要以函数实际读取核对完整性，不能仅凭表格建缓存键。

提交检测与内容复用分两层：整库提交代次负责发现“可能有变化”；内容指纹负责判断某个计算步骤的输入“确实变了”。两者都保留。日期只有在某个步骤确实依赖该日期时进入该步骤的键；不能仅因发现日期键较宽，就删除近期原题窗口或模型时间权重。

两处重要限制：

- 群体模型有全体依赖。观测变化后需判断完整模型输入，相关变化仍须重算全体模型。模型输出不变时才能复用依赖它的计算。
- 自动分组有顺序依赖。一个学生的候选或水平变化可能改变后续组员选择。可复用题目特征和固定匹配，不能直接保留“其他学生原来的组”。

公开来源与内部计算结果也要分开处理。教师改了扣分说明，即使数值模型输入未变，诊断正文及相关推荐理由仍要刷新。题库提交修订导致来源版本变化，即使选题核心输入未变，也要按当前规则生成来源版本，不能把旧整份响应改一个缓存标签后直接返回。

## 4. 可重建的只读计算资料

“派生读模型”是从原始资料整理出来、专门供读取和计算使用的资料。原始资料仍是依据，派生资料损坏后可以重建。本项目已有只读投影和快照，建议先复用这些能力，避免另建一套数据归属。

建议先在现有题库与训练模块内部整理紧凑资料：候选正文和来源引用只存一次；候选条目存标识与数值；最终响应再组装原字段。这样能减少逐生逐目标深拷贝，也有利于数组计算。内部共享前必须确认调用方不会修改这些对象。

如果现有快照不能容纳后续跨请求结果，再评估独立、可删除重建的本地缓存存储。不是在考试数据库或题库数据库中批量写入新的推荐状态。缓存缺失、损坏、写入失败仍回退原计算；已发生的真实数据变化必须检测。

SQLite 原生视图保存查询定义，读取时执行查询；单纯 `CREATE VIEW` 不会把昂贵计算结果预先保存。需要持久保存派生结果时，必须由应用明确维护缓存或派生表。[SQLite CREATE VIEW](https://www.sqlite.org/lang_createview.html)

SQL 侧先用 `EXPLAIN QUERY PLAN` 区分全表扫描、索引查找与覆盖索引，再根据实际查询优化。不能仅凭“冷读约 20 秒”断言缺索引；正文、图片检查、Python 组装也可能占主要时间。[SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)、[SQLite 查询规划](https://www.sqlite.org/queryplanner.html)

SQLite 的 `data_version` 只适合在同一长期连接的两个时间点之间比较，并不直接提供发生变化的业务行。本项目已经封装了提交检测，建议沿用，再补充内容依赖核对。[SQLite PRAGMA data_version](https://www.sqlite.org/pragma.html#pragma_data_version)

若将来考虑触发器记录精确变更，SQLite 支持按表的 INSERT、UPDATE、DELETE 触发器。但这是新增源数据库维护机制，涉及迁移和既有写流程。本轮不建议先做。WAL 能让读与写同时进行，但仍只有一个写入者，也不提供多个数据库整体的原子事务；不能靠开启 WAL 解决 Python 计算或跨库一致性。[SQLite CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html)、[SQLite WAL](https://www.sqlite.org/wal.html)

## 5. 六个开源项目的具体取舍

| 项目 | 已核实的能力 | 本项目适用方式 | 主要限制 |
|---|---|---|---|
| Bazel / Skyframe | 显式依赖、变更传播、中间值不变时停止传播 | 借鉴缓存输入与失效设计 | 不直接接入推荐运行时；完整依赖需自行梳理 |
| SQLite | 索引、只读事务、视图、触发器、WAL | 继续使用已有数据库与投影；先查 SQL 计划 | 视图不会预存复杂结果；`data_version` 不报告业务行；WAL 不加速 Python 热点 |
| joblib Memory | 按函数输入持久保存结果，支持 NumPy 和只读内存映射 | 若需要保存大数组，评估局部纯函数 | 不能替代业务依赖识别；不能默认保证同键并发只算一次 |
| DiskCache | 本地持久缓存、跨线程与进程访问、原子操作和锁 | 只有已有缓存组件不足时才评估 | 缓存存储不会自动发现真实来源变化；默认防拥挤策略不等于严格最新结果 |
| Numba | 编译支持的 Python / NumPy 数值循环 | 当前数组热点确认后做小范围对比试验 | 全引擎不能直接套用；编译、打包和浮点一致性需要核验 |
| RoaringBitmap / PyRoaring | 整数集合的交、并、差与直接计数 | 加速候选交集、成员覆盖集合、重复题集合 | 集合遍历顺序不能替换推荐排序；几百道题未必需要新增库 |

前两项的官方依据见第 3、4 节，后四项的依据及判断如下。

### joblib：适合纯函数数组结果，不能承担完整正确性

官方建议把缓存应用于明确输入的纯函数；支持 NumPy 输入哈希和只读内存映射。库或依赖升级可能使缓存键变化；Windows 还需要正确释放内存映射文件。[joblib Memory 官方文档](https://joblib.readthedocs.io/en/stable/user_guide/memory.html)

查看 joblib 1.6.0 的 `MemorizedFunc._cached_call` 与 `_call`：未命中后直接执行函数，再写入结果。根据这条源码路径，不能把 `Memory.cache` 当作“多个请求同时未命中，只执行一次”的保证。它也没有完整业务依赖图，数据库、外部文件和辅助规则仍需作为显式输入或计算版本纳入。[joblib 1.6.0 memory.py 源码](https://raw.githubusercontent.com/joblib/joblib/1.6.0/joblib/memory.py)

当前候选数量为几百道，尚未证明加载大数组是主要耗时。因此建议先改善现有对象与数组结构，不先把整个 `PersonalizedRecommendationModule` 用 `Memory` 装饰。

### DiskCache：存储与锁成熟，失效仍由应用负责

`Cache` 支持跨线程、跨进程使用，并提供原子操作及同步锁。`FanoutCache` 通过分片减少写入阻塞，但超时可能使 `set` 或 `delete` 放弃；事务还不能跨分片整体使用。[DiskCache 官方教程](https://grantjenks.com/docs/diskcache/tutorial.html)

`memoize_stampede` 官方定义是过期前的概率性后台重算。源码在尚未过期时可返回现有值；冷未命中会执行原函数。这不等于“相关数据一变，就等待新结果”。因此不能用一个到期时间替代来源变化检查。[DiskCache API](https://grantjenks.com/docs/diskcache/api.html)、[DiskCache recipes.py 源码](https://raw.githubusercontent.com/grantjenks/python-diskcache/master/diskcache/recipes.py)

本项目已有同键共算。若将来确有跨进程需要，建议使用按内容键区分的锁：查有效缓存、取得该键锁、再次查缓存、计算、核对来源未变、发布结果。长计算不占用缓存数据库写事务。需要处理失败和进程退出，不能只给所有参数共用一把全局锁。这是本项目设计建议，未实施。

### Numba 与 NumPy：先消除对象循环，再决定编译

NumPy 广播能把部分循环移到原生运算，但官方也说明，大型中间数组会造成额外内存开销，不是所有广播都更快。[NumPy 广播说明](https://numpy.org/doc/stable/user/basics.broadcasting.html)

Numba 官方要求先测真实热点；支持的数值循环可用 `nopython` 编译。`fastmath` 放宽浮点规则，并行归约可改变累加顺序。[Numba 性能说明](https://numba.readthedocs.io/en/stable/user/performance-tips.html)

推荐计算包含混合业务字典、来源引用、深拷贝和文本匹配。应先抽出连续数值数组及整数标识，保留原运算与排序顺序。先比较 NumPy 或普通紧凑循环，再测试局部 Numba。默认关闭 `fastmath` 和会改变归约顺序的并行；即便关闭这些选项，也要核对难度阈值、并列排序和完整输出。

Numba 的磁盘缓存保存的是编译代码，不能替代业务结果缓存。官方还列出跨文件符号变化可能不被缓存失效识别、全局变量按编译时常量保存等限制。因此规则和参数应显式传入，并沿用项目计算版本核对。[Numba 编译缓存说明](https://numba.readthedocs.io/en/stable/developer/caching.html)

掌握度拟合已有 NumPy；交接文档记录此前全体拟合约 1.4 秒。建议优先调查分组、候选组装、复制和资料准备，不把模型拟合当作首要瓶颈。

### RoaringBitmap：借鉴集合运算，先评估轻量实现

CRoaring 提供压缩位图，也支持普通位图；官方指出普通位图在部分情形下查询更快。PyRoaring 是其 Python 包装，支持 Windows，并提供不生成完整交集就能计数的接口。[CRoaring 官方项目](https://github.com/RoaringBitmap/CRoaring)、[PyRoaring 官方项目](https://github.com/Ezibenroc/PyRoaringBitMap)、[PyRoaring intersection_cardinality](https://pyroaringbitmap.readthedocs.io/en/latest/#pyroaring.AbstractBitMap.intersection_cardinality)

对当前两章合卷 476 道候选，可先把题目映射到稳定的内部序号，用 Python 整数位集合或 NumPy 布尔数组表达“可选题”“覆盖技能”“近期原题”。Python 已支持整数按位运算和 `int.bit_count()`。[Python 整数类型](https://docs.python.org/3/library/stdtypes.html#int.bit_count)

这是待测方案。已有 `set` 可能已经足够快，数据转换也会占时间。位图仅替换集合判断；选题仍按原候选顺序和排序键执行。不能按位图默认升序输出题目。

## 6. 为什么不默认选择其他热门组件

| 组件 | 适合解决的问题 | 当前不优先的原因 |
|---|---|---|
| Redis | 多服务共享缓存、远程数据结构 | 单机已有本地缓存；换存储介质不能减少 36.8 秒的分组重算。官方 Windows 路径包含 Memurai 和 WSL，增加独立服务维护。[Redis Windows 官方文档](https://redis.io/docs/latest/operate/oss_and_stack/install/archive/install-redis/install-redis-on-windows/) |
| Celery | 后台任务、重试、调度、多机器执行 | 项目已有预热。完整最新结果仍需等计算完成，队列本身不缩短计算。官方明确 Windows 不受支持。[Celery 官方 FAQ](https://docs.celeryq.dev/en/stable/faq.html#does-celery-support-windows) |
| Faiss / 向量检索 | 向量距离的近邻检索 | 目前是技能、难度、原题和整卷规则，不是单一向量距离。官方对少量搜索建议直接计算，近似索引存在速度与准确率取舍；即使使用精确 Flat，也不能直接替换本项目评分与排序。[Faiss 官方索引选择说明](https://github.com/facebookresearch/faiss/wiki/guidelines-to-choose-an-index) |
| OR-Tools CP-SAT | 为明确定义的整数约束寻找可行或最优解 | 它会求解另一个数学目标。现有贪心顺序和局部替换是当前规则的一部分，不能保证逐项结果相同。CP-SAT 约束需要整数表达，还需处理数值转换。[OR-Tools 官方 CP-SAT 说明](https://developers.google.com/optimization/cp/cp_solver/) |

上表是结合项目约束的判断，不是这些项目的普遍性能评价。未来允许改变推荐规则、服务运行方式或数据规模时，可以重新评估。

## 7. 现有复用候选与实施顺序建议

本轮不建议新建通用服务、接口、注册表或策略层。已有入口与实现可承担第一轮工作：

| 已有实现 | 可复用能力 | 建议扩展方向 |
|---|---|---|
| [question_tag_projection_service.py](../../integration/question_tag_projection_service.py) 与 [question_skill_index.py](../../question_bank/services/question_skill_index.py) | 题目关联、资料读取与只读投影 | 尽量从现有投影整理推荐计算资料，避免另走一遍题库正文与关联读取 |
| [result_cache.py](../../integration/result_cache.py) | 有容量限制的结果缓存与同键共算 | 在现有热点内部加完整内容键；需要持久化时先评估现有快照能力 |

建议先执行一个小范围性能试验，再决定下一步投入：

1. 重新采集当前分组和草稿热点；把提交检测、资料读取、计算、对象组装、校验、压缩和传输分开计时。
2. 优先试验候选固定资料共享、掌握度快照共用、来源与候选固定评价的内容复用。以现有完整输出比较验证收益。
3. 若分组冷计算仍由集合判断和排序循环主导，再试验紧凑数组或位集合；之后才评估 Numba。
4. 若冷读仍占主要时间，再决定是否需要持久化新的派生资料，以及是否需要精确变更记录。涉及真实数据库迁移时按 AGENTS.md 单独授权。

## 8. 如何判定方案是否解决等待

必须分别测量：完整响应有效缓存命中；候选资料有效但分组重算；相关证据变化后的重算；题目资料变化后的重算；全新范围首次计算；正式页面完整显示。不能把第一项的秒数当作其他场景的性能。

性能目标可以设为工程试验门槛，但目前没有证据承诺“完整最新页面 2 秒”或某个加速倍数。需要用同一工作机、相同输入、相同时间条件、多次运行记录中位耗时和较慢样本，并单列机器负载和后台预热状态。

正确性验收沿用完整配对比较。还要覆盖：无关提交后可复用计算但来源仍核验；有意义的题目或证据变化必须重算；仅描述变化时公开正文刷新；单生观测影响全体模型；计算期间来源变化；并发同键请求、重启恢复、缓存损坏与保存失败。所有输出字段按现有规则比较，不能只比较题目集合。

实施验证已覆盖完整推荐输出比较、首章完整页面和合成缓存失效回归。真实题目更新、新增作答后的页面计时尚未完成。当前实现以 `ARCHITECTURE.md` 为准，测试入口以 `docs/testing/README.md` 为准，测量口径以交接文档为准；本文保留备选方案及其适用条件。
