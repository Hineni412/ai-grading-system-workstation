# P1-23 Ops 受保护写操作设计

**日期：** 2026-07-12
**执行包：** P1-23
**状态：** 已获用户逐节批准，等待书面规格复核
**用户自测：** none

## 1. 目标

为本机 FastAPI Ops 能力增加受保护的备份、恢复、数据库迁移、数据包导入和数据包导出。所有操作必须先预检，再由短期确认令牌提交独立 Job；恢复、迁移和导入不得在 Streamlit/FastAPI 正在使用数据库时直接替换正式数据。

本设计不改变现有 Streamlit 业务行为、评分规则、题号契约、知识点语义、数据库 Schema 或单用户 loopback 部署边界。自动验证只使用临时数据根和临时本机状态区，不执行任何真实 `user_data/` 操作。

## 2. 权威要求与本包设计选择

### 2.1 仓库已规定的硬性要求

以下内容来自 P1-23 执行包定义和当前执行索引：

- 备份、恢复、迁移、数据包导入和导出通过独立 Job、预检和确认令牌承载。
- 每类操作先 dry-run；执行前备份；限制目标根目录；返回结构化结果和恢复说明。
- 备份失败必须阻断恢复或导入；路径越界必须拒绝；迁移必须通过副本预演和完整性检查。
- 不开放任意命令执行，不自动操作真实数据库，不默认包含 Phase 6 数据。
- P1-23 只允许白天人工监督；真实数据操作需要针对具体动作重新获得用户明确授权。
- 开发、测试和集成验证只使用临时数据根，真实两库指纹必须保持不变。

### 2.2 用户已批准的本包设计选择

以下内容不是既有文档原句，而是本设计为落实硬性要求所做的选择：

- 确认令牌单次使用、有效期 5 分钟，并绑定完整预检内容和资源指纹。
- 使用服务端短期预检计划；客户端不携带内部路径或完整执行计划。
- 备份和数据包导出在线完成；恢复、迁移和数据包导入先准备，再于下次受控启动前离线落地。
- 五类 Ops 写任务共用一个运维操作锁，避免相互交错。
- 离线操作日志保存在不会被数据恢复覆盖的本机状态区。
- 离线操作失败时先自动回退；回退也失败则阻止应用继续启动并输出脱敏人工恢复说明。

## 3. 设计原则

1. **安全标识代替路径。** API 只接受备份文件名、迁移目标枚举、导出范围枚举、服务器上传资源 ID 和确认令牌。
2. **预检与提交内容一致。** 操作、参数、源资源指纹、目标数据代际或迁移集合在预检到 Job 提交之间发生变化时，旧令牌失效。准备完成到重启之间允许正常应用活动；离线应用器必须针对当时的最新目标重新预检并重新备份。
3. **先完整准备，再发布。** ZIP、导入内容、恢复内容和迁移候选都先写入暂存区并完成验证，禁止边读取边覆盖正式数据。
4. **正式数据库离线替换。** Streamlit 和 API 启动前才允许恢复、迁移或导入触及正式数据库文件。
5. **失败可解释、可回退。** 每个危险操作必须有操作前备份、操作日志、明确恢复来源和可测试的故障注入边界。
6. **公开信息最小化。** 公开响应不包含内部路径、密钥、业务正文、ZIP 成员正文或原始异常。
7. **不扩大产品范围。** 本包只建立后端受保护写能力，不新增运维页面、不切换生产 UI、不接入 Phase 6 数据。

## 4. 总体架构

### 4.1 组件

#### OpsPreflightService

负责：

- 解析固定操作类型和严格请求模型；
- 对备份、恢复、迁移、导入和导出分别执行无正式数据写入的 dry-run；
- 计算资源指纹、预计文件数/字节数、迁移集合和风险摘要；
- 把完整内部计划交给 `OpsPlanStore`，仅向客户端返回安全摘要和确认令牌。

#### OpsPlanStore

进程内、带锁的短期计划存储：

- 令牌使用密码学随机值；服务端只按令牌摘要索引；
- 计划创建后 5 分钟过期；
- 成功提交时原子标记已使用，重复提交返回稳定冲突；
- 计划绑定操作类型、规范化安全参数、资源指纹、目标代际和生成时间；
- API 进程重启时全部计划失效。

计划存储不进入 `jobs.payload_json`，不保存密钥、绝对路径或业务正文。

#### OpsOperationCoordinator

负责：

- 消费并复核预检计划；
- 获取进程内 Ops 锁和跨进程文件锁；
- 再次核对资源与目标代际；
- 提交五类独立 Job；
- 为离线操作创建不可变操作 ID、暂存目录和签名/校验后的操作清单；
- 生成固定公开结果和恢复说明代码。

跨进程文件锁用于避免 API Ops Job 与启动前离线应用器并行，但不宣称能让现有 Streamlit 业务代码进入维护模式。因此恢复、迁移和导入仍必须在双进程启动前落地。

#### 在线 Job handlers

- `ops_backup`
- `ops_transfer_export`

在线 handler 只向 Job 专属暂存目录写入，完成后原子发布产物。产物通过现有受控 Job 下载入口访问。

#### 离线准备 Job handlers

- `ops_restore_prepare`
- `ops_migration_prepare`
- `ops_transfer_import_prepare`

这些 handler 不替换正式数据。它们完成操作前备份、暂存、候选执行、完整性检查和操作清单发布，结果为 `prepared_restart_required`。

#### OpsOfflineApplier

由 `运行.bat` 在启动 Streamlit 和 FastAPI 之前调用的固定 Python 入口：

- 没有待处理操作时快速、无副作用退出；
- 按单一待处理清单执行固定操作，不接受任意命令或客户端路径；
- 在触及正式目标前，针对最新目标重新执行必要预检并创建新的应用时备份；
- 执行成功后原子记录结果，再允许应用启动；
- 执行失败时使用应用时备份回退；
- 回退失败时非零退出并阻止后续服务启动。

#### OpsOperationJournal

保存离线操作的最小状态：`operation_id`、操作类型、准备/应用/回退状态、时间、公开结果代码、清单摘要和恢复备份标识。内部执行清单可包含受控绝对路径，但只保存在本机状态区，永不直接投影到 API。

本机状态区使用 `PathManager` 新增的明确逻辑路径，默认解析到 `%LOCALAPPDATA%/AIGradingSystem/ops`，位于数据恢复范围之外；测试必须显式覆盖为临时目录，不得把解析后的本机绝对路径写入仓库配置、公开响应或文档证据。

### 4.2 数据流

1. 客户端上传导入包或选择已有备份/迁移目标/导出范围。
2. 客户端请求预检。
3. 服务在临时目录或稳定 SQLite 候选上执行 dry-run，生成安全摘要和 5 分钟确认令牌。
4. 客户端提交令牌。
5. 服务原子消费令牌、复核指纹并提交对应 Job。
6. 在线操作生成并原子发布文件；离线操作生成准备时安全备份、验证暂存内容并发布待重启清单。
7. 下一次启动时离线应用器针对最新目标重新预检、创建应用时备份，再在两个应用进程打开数据库前完成替换或迁移。
8. 应用启动后通过操作 ID 查询外部 Journal 的最终状态；Job 公共结果只返回操作 ID、结果枚举、计数、安全文件名和受控 URL。

## 5. API 契约

### 5.1 导入包暂存

`POST /api/ops/transfer-import/uploads?filename=<safe-name>`

- 使用原始请求流，不把整个上传先读入内存；
- 限制为 ZIP，默认最大 200 MiB；
- 写入受控暂存根并在发布前计算 SHA-256；
- 返回 `upload_id/filename/size_bytes/sha256`，不返回路径；
- 上传失败清理临时文件，不留下可执行资源。

### 5.2 统一预检

`POST /api/ops/preflights`

请求采用带判别字段的严格联合模型：

- `backup`：只接受固定 reason 枚举，不允许包含 API key；
- `restore`：只接受当前受控备份清单中的 `backup_filename`；
- `migration`：只接受 `grading/question_bank/all`；不接受迁移目录或 SQL；
- `transfer_import`：只接受 `upload_id`；
- `transfer_export`：只接受 `lean/full`。

响应包含：

- `operation`
- `confirmation_token`
- `expires_at`
- `requires_restart`
- `summary`：固定字段的文件数、总字节数、数据库目标、待执行迁移数、警告代码和预期结果

响应不包含计划 ID、内部路径、ZIP 成员完整列表、SQL、密钥或正文。

### 5.3 提交 Job

`POST /api/ops/jobs`

请求只含 `confirmation_token`。成功返回现有 `JobResponse`。通用 `POST /api/jobs/{job_type}` 必须拒绝五类 Ops Job，防止绕过预检。

### 5.4 离线操作状态

`GET /api/ops/operations/{operation_id}`

返回：

- `operation_id`
- `operation`
- `status`：`prepared/restart_required/applying/applied/rolled_back/failed`
- `result_code`
- `created_at/updated_at`
- `recovery`：固定说明代码和安全备份文件名（如存在）

不存在或不是安全 UUID 时返回统一 404/422。

`POST /api/ops/operations/{operation_id}/cancel`

只允许撤销 `prepared/restart_required` 且尚未进入 `applying` 的操作；原子移除 pending 标记并清理该操作暂存资源，但保留准备时安全备份和 Journal。已经开始离线应用时返回 409，不能把取消解释为强行中断文件替换。

### 5.5 文件下载

在线备份或数据包导出成功后，Job 公共结果返回安全文件名和 `/api/jobs/{job_id}/download`。文件服务只解析 Job ID，并验证 Job 类型、成功状态、固定 Ops 输出根、文件扩展名和真实路径；不接受下载路径参数。

## 6. 各操作设计

### 6.1 备份

预检：

- 枚举固定备份源；
- 计算将包含、跳过和敏感跳过的文件数与总大小；
- 对数据库使用稳定候选读取，不创建正式备份目录或日志文件；
- 绑定当前数据库和源文件代际摘要。

执行：

- 为两个 SQLite 数据库生成一致性快照，而不是直接压缩可能变化的 main/WAL/SHM；
- 其他文件按受控根和跳过规则写入 Job staging ZIP；
- 对 ZIP 做 CRC/成员清单校验；
- 原子发布到受控备份根；
- 取消只在正式发布前确认。

### 6.2 数据包导出

预检复用当前 `lean/full` 选择规则，但所有条目必须再次通过受控根、reparse point 和敏感文件守卫。执行写入 Job staging ZIP，验证后发布到 Ops 输出根；不默认包含 Phase 6 数据或本机 API profiles。

### 6.3 恢复

预检：

- 备份必须来自受控备份清单；
- 完整检查 ZIP 结构、成员类型、目标根、重复目标、大小、压缩比例和数据库候选完整性；
- 明确列出将覆盖的类别和数据库数量，不返回成员路径；
- 不写正式目标。

准备 Job：

- 首先创建并验证当前数据的一致性准备时安全备份；失败即终止；
- 解压到操作专属暂存目录；
- 对候选数据库执行 `quick_check/integrity_check` 和必要表检查；
- 写入不可变待重启清单。

离线应用：

- 针对当时的最新正式目标重新执行恢复预检；
- 创建并验证新的应用时备份；失败即不触及正式目标；
- 再次验证清单、暂存内容和两个安全备份；
- 采用同卷原子替换或逐文件可回退替换；
- 任一文件失败立即按 Journal 使用应用时备份反向恢复已替换项；
- 成功后清理 pending 标记，保留审计、准备时安全备份和应用时备份。

恢复保持当前兼容语义：只覆盖备份中明确包含的受控文件，不删除备份中不存在的现有文件。任何“镜像式恢复并清除多余文件”都属于破坏性新语义，不在 P1-23 范围内。

### 6.4 数据库迁移

预检：

- 把每个目标数据库捕获到临时候选；
- 在候选副本上执行待执行迁移，不允许 `run_migrations(dry_run=True)` 打开正式库；
- 拒绝现有迁移引擎识别的破坏性 SQL；
- 执行 `integrity_check`、迁移记录和预期 Schema 核对；
- 绑定迁移文件名和校验和集合。

准备 Job 创建准备时数据库安全备份和迁移计划。离线应用器重新验证迁移文件校验和，在最新正式数据库候选上重跑预演并创建应用时数据库备份后，才对正式库执行固定迁移目标。`all` 目标视为一个受保护操作：任一数据库迁移失败时恢复本次涉及的全部数据库应用时备份并阻止启动，不能留下跨库半完成状态。

### 6.5 数据包导入

预检：

- 只接受服务器暂存的 ZIP 资源；
- 限制总上传大小、成员数量、单成员展开大小、总展开大小和压缩比例；
- 拒绝绝对路径、`..`、未知顶层根、符号链接/reparse point、重复规范化目标和大小写碰撞；
- 对候选数据库做完整性检查；
- 不允许导入 API profiles 或 Phase 6 数据。

准备 Job 必须先创建当前数据的准备时安全备份，再把内容完整解压到专属暂存区。离线应用器针对最新目标重跑导入预检并创建应用时备份后，使用与恢复相同的 Journal 和回退协议；不允许 Streamlit 当前的“备份失败继续导入”兼容行为进入新 API。导入同样只覆盖包内明确包含的受控文件，不删除其他现有文件。

## 7. 并发、取消与重启

- `OpsOperationCoordinator` 使用一个进程内锁和一个本机状态区文件锁；同一时间只允许一个 Ops 写 Job 或离线应用器持有。
- 已有 Ops 写 Job 时，新提交返回 `ops_operation_busy`，不排队制造多个待执行危险操作。
- queued Job 可按现有 JobManager 规则取消；running Job 在暂存、候选验证和发布/清单提交前检查取消。
- 在线文件已原子发布后，正常成功可以赢得取消竞态。
- 离线准备清单发布后不再把普通 Job 取消解释为删除待执行操作；取消待重启操作必须使用专用操作撤销入口。该入口仅删除尚未 applying 的 pending 清单和暂存资源，不删除准备时安全备份。
- API 进程重启使未消费确认令牌失效，旧 queued/running Job 按现有规则标为 failed。
- 启动前离线应用器只处理一个合法 pending 操作；发现多个、清单损坏或状态不明时拒绝启动并要求人工检查。

## 8. 安全边界

- API 请求模型 `extra="forbid"`；所有操作和参数使用枚举或固定格式。
- 不接受 `path/destination/command/sql/migrations_dir` 等客户端字段。
- ZIP 校验不得依赖 `extractall()`；每个成员先规范化、验证，再写入暂存区。
- 解析后路径必须位于精确受控根，并拒绝符号链接、junction 和其他 reparse point 越界。
- 公开 Job payload/result 使用显式允许列表；错误只返回稳定代码和通用说明。
- 日志不得记录确认令牌、内部清单全文、密钥、学生姓名、答卷、题目正文或 ZIP 成员正文。
- API profiles 永不进入备份、导入、导出或公开响应。
- Phase 6 数据默认无来源定义，因此任何未知顶层根一律拒绝，不做自动推断。

## 9. 失败与恢复

公开错误至少包括：

- `ops_confirmation_expired`
- `ops_confirmation_used`
- `ops_preflight_stale`
- `ops_resource_not_found`
- `ops_operation_busy`
- `ops_pre_backup_failed`
- `ops_integrity_check_failed`
- `ops_archive_invalid`
- `ops_offline_apply_failed`
- `ops_offline_rollback_failed`

错误映射规则：

- 参数/格式错误：422；
- 资源不存在：404；
- 令牌已用、计划变化、操作占用：409；
- 临时存储或安全边界不可用：503；
- 内部异常不回显，只在本机受控日志记录脱敏摘要。

离线应用失败但回退成功时状态为 `rolled_back`，应用可以继续启动并提示操作未生效。回退失败时状态为 `failed`，离线应用器返回非零，`运行.bat` 不启动 Streamlit 或 API。

## 10. 测试与验收

### 10.1 单元与服务测试

- 令牌 5 分钟过期、单次消费、并发消费、重放和进程重启失效；
- 参数、上传、备份、数据库或迁移文件变化导致 `ops_preflight_stale`；
- Ops 锁的并发提交、取消和释放；
- 备份数据库一致性快照、ZIP CRC、原子发布和发布前取消；
- 导出 lean/full 兼容和敏感文件排除；
- 导入/恢复的路径穿越、绝对路径、符号链接、junction、ZIP bomb、重复目标、大小写碰撞和未知根；
- 备份失败严格阻断恢复/导入；
- 迁移候选执行、破坏性 SQL 拒绝、校验和变化和完整性检查；
- 离线应用的成功、替换中断、自动回退成功、回退失败和多 pending 拒绝。

### 10.2 API 与公开数据测试

- 严格请求/响应模型和统一错误体；
- 通用 Job 端点拒绝所有 Ops 专用 Job；
- Job payload/result、操作状态和 OpenAPI 不含路径、命令、SQL、token、secret、password、业务正文；
- 上传流限制、受控下载和 `Cache-Control: no-store`；
- P1-22 只读自检与备份清单保持兼容。

### 10.3 启动与回归测试

- `运行.bat` 无 pending 操作时保持现有双入口和 `START_API=0` 行为；
- pending 成功时先应用再启动；回退失败时不启动；
- JobManager queued/running/restart 状态继续符合 P1-11；
- 聚焦测试、受影响 API/迁移/数据传输/启动回归、`git diff --check` 和 `tools/smoke_check.py --skip-tests` 通过；
- integration 波次执行完整 `tools/smoke_check.py`，并按高风险迁移/启动入口触发条件保留完整测试证据。

### 10.4 数据守卫

- 所有写测试显式注入 `tmp_path` 数据根和临时本机状态区；
- 不调用真实 Ops 端点，不使用真实密钥或真实模型；
- 实施、复审、集成前后都只读记录根目录两库的大小、UTC 修改时间和 SHA-256；
- 任一真实数据库指纹变化、`user_data/` 新增修改、提交或 stash 都是阻塞失败。

## 11. 用户影响

P1-23 只提供后端能力，不新增可见页面，因此本包用户自测为 `none`。未来 P2-19 运维页面接入时，应把“预检—确认—后台准备—需要重启—最终结果/回退”展示为清晰步骤，不能把 Job `succeeded` 简化为“危险操作已经落地”。

真实数据操作不因本包实现而自动获得授权。每次真实备份、恢复、迁移或数据传输仍须说明目标、影响、备份和回退方式，并获得用户对该具体动作的明确授权。

## 12. 回退

- 代码回退：P1-23 独立提交链整体回退；未生成 pending 操作时不改变持久数据格式。
- 在线产物回退：未发布的 staging 直接清理；已发布备份/导出作为普通受控产物保留或由后续明确操作删除。
- 离线准备回退：在 `prepared/restart_required` 状态可显式撤销 pending 清单和暂存内容，保留准备时安全备份。
- 离线执行回退：使用最新应用时备份和 Journal 反向恢复；失败时停止启动并保留现场。
- 设计回退：若启动前离线应用器被证明超出 P1-23 可控范围，则不得退化为在线覆盖；应停止实现并重新拆包，而不是削弱数据安全门槛。
