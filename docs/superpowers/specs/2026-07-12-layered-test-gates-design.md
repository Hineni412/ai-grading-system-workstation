# 分层测试门禁设计

**日期：** 2026-07-12

**状态：** 已实施并完成静态验证
**范围：** 后续所有正式执行包的开发、复审与集成验证流程

## 目标

在不降低合并可信度和真实数据保护要求的前提下，避免同一代码和同一基线在功能开发、独立复审、文档交接、集成与主线同步阶段重复运行耗时超过 200 秒的全量测试。

## 规则设计

1. 功能分支开发过程中使用当前测试、包内聚焦测试和受影响回归获得快速反馈。
2. 功能分支交接前运行包内验收、相关回归、`git diff --check` 和 `tools/smoke_check.py --skip-tests`，默认不运行全量 pytest。
3. 独立复审修复后只重跑能够覆盖修复和影响面的测试；纯文档、交接状态或提交整理不触发全量测试。
4. integration 每合入一个包立即运行该包聚焦回归和受影响命令；当前集成波次全部合入后只运行一次完整 `tools/smoke_check.py`。
5. 完整测试证据只有在被验证的代码 SHA、依赖基线和测试配置相同且其后无实质代码变化时才可复用。
6. 出现以下任一情况时允许或要求额外全量测试：上次全量后发生实质代码变化；合并冲突后手工改代码；公共基础设施、依赖锁、数据库 Schema、核心状态机或跨域共享入口发生变化；全量测试失败或出现不稳定现象；最终候选 SHA 与已验证 SHA 不一致；执行包定义明确要求独立全量门禁。
7. 删除、破坏性迁移和其他包定义明确标记的高风险操作继续保留其专项全量测试与真实数据副本门禁。

## 文档落点

- `AGENTS.md`：增加长期测试原则和完整测试证据复用条件。
- `docs/superpowers/packages/README.md`：把分层测试写入标准执行包流程。
- `docs/superpowers/packages/PARALLEL_WORKTREE_EXECUTION.md`：明确功能分支、逐包集成、波次全量和额外全量的判断条件。
- `docs/superpowers/plans/2026-07-03-frontend-backend-modernization-master-plan.md`：修正“每个 WP/每次提交都跑全量”的旧表述，使其服从当前执行包和 integration 门禁。

P1-16 的历史实施记录与测试证据保持不变。

## 验收

- 四处规则没有互相矛盾。
- 后续任务可以明确判断何时跑聚焦、受影响和完整测试。
- 文档明确禁止因复审、纯文档提交或主线同步重复全量测试。
- 删除和迁移等高风险例外不被削弱。
- 本次文档变更只运行文档搜索、一致性检查和 `git diff --check`，不运行全量 pytest。
