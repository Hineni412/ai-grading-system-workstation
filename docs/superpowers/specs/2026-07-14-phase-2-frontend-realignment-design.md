# Phase 2 前端来源重校准门槛设计

> **工作类型：** 一次性、非编号、白天人工通过的治理与纠偏门槛；不是正式执行包。
> **插入位置：** P2-08 已合并之后，P2-09 及其他复杂页面继续迁移之前。
> **计数与自动化：** 不改变 Phase 2 的 22 包和全局 87 包计数，不进入夜间资格矩阵，不使用正式包交接块。
> **用户决定：** 2026-07-14，用户确认需要校正文档和参考图，并要求在已合并的 P2-08 之后增加修改环节；同时明确现有 Streamlit、服务、数据库契约和测试提供业务能力与结果基线，已完成 Vue 页面只是待核验的能力清单和初步原型。新前端应在新架构下主动优化信息架构、布局和操作。

## 1. 背景与问题

P2-08 已经通过当时的自动验证、用户验收并进入主线。该事实和证据保持不变，不回写为未完成，也不重开 P2-08。

但复盘确认，AI 生成的完整概念图虽然被标注为“视觉参考”，其中的页面结构、导航、字段、操作和工作流仍被后续计划当成了实现依据。`STYLE.md` 也混入了固定信息架构、单题三栏流程和快捷键等功能性内容，导致“参考样式”事实上扩张成了“功能设计”。

现有 Streamlit 的阅卷业务事实是按题号批量复核。P2-05 至 P2-08 已实现的单份记录三栏页可以保留为可复用能力或可选详情，但不能未经业务确认就取代批量复核成为默认主流程。

本次纠偏也不能走向另一个极端：现有 Streamlit 和 P2-03 至 P2-08 Vue 页面都不是必须逐屏、逐控件或逐点击复刻的设计模板。现有 Streamlit、服务、数据库契约和测试用于确认教师必须完成的任务、数据含义、业务动作与结果、状态语义、安全确认和失败恢复；P2-03 至 P2-08 Vue 页面只提供待核验的能力清单和可复用原型，不能单独证明业务事实。新 Vue SPA 的价值正是借助新架构重新组织页面、减少不必要步骤并改善桌面操作体验。

## 2. 决策

在 P2-08 和后续复杂页面迁移之间增加“Phase 2 前端来源重校准门槛”。门槛未通过时，P2-09、P2-13、P2-14、P2-16、P2-19 以及它们的后续依赖均不得开始实现或由夜间自动化领取。

这不是 P2-23、P2-08A，也不重定义 P2-09。原因是它属于一次性方向纠偏，不是新的长期产品能力；正式包编号、职责、状态和 87 包统计必须保持稳定。

## 3. 重新确立的三层设计权威

### 3.1 必须继承：业务能力与结果基线

现有 Streamlit、服务实现、数据库契约和测试用于确认：

- 教师需要完成的真实任务和必须可达的业务能力；
- 数据字段的含义、输入输出和持久化结果；
- 业务动作、状态语义、权限与安全边界；
- 危险操作确认、失败恢复、幂等和审计要求；
- 已知边界条件和兼容行为。

这些内容不得因为换前端而丢失、改义或被无来源功能替代。旧 UI 的框架限制、重复步骤、控件位置和使用不便不属于必须保留的业务事实。

P2-03 至 P2-08 已实现 Vue 行为只能作为审计输入和复用候选；只有回溯到上述业务来源，或已有用户明确决定支持的部分，才能进入业务基线。

### 3.2 允许重设计：信息架构与操作体验

在必要业务能力可达、数据语义和结果等价、安全边界不降低的前提下，新 Vue SPA 可以主动：

- 重新分组导航，合并或拆分页面；
- 选择更合适的一栏、多栏、主从、抽屉或渐进披露结构；
- 调整字段和操作的呈现顺序、控件形式与位置；
- 减少不必要步骤，改善批量处理、上下文保持和错误恢复；
- 为已有业务动作提供更合适的桌面快捷方式，但不得绕过确认或安全保护；
- 修正旧原型中已经证明低效、含混或受 Streamlit 框架限制的交互。

这些 UX 差异不要求与旧 UI 一一对应，也不要求每个控件获得专项用户决定；必须记录设计理由，并通过设计复审、浏览器验证和用户验收证明更清楚、有效且不丢功能。

### 3.3 视觉权威

`docs/ui/STYLE.md` 只约束颜色、字体、间距、密度、边框、圆角、阴影、控件外观、焦点、动效、可访问性和通用视觉质量。参考图只能帮助判断这些视觉属性，不能证明系统需要某个导航、页面、字段、按钮、状态、快捷键或流程。

### 3.4 用户专项决定的边界

只有新增或删除业务能力，改变数据含义、业务结果、状态语义、权限、安全边界、持久化方式或危险操作保护时，才必须取得带日期与范围的用户专项决定。纯信息架构、布局、控件和操作优化不需要逐项批准，但仍须接受设计复审和最终用户验收。

每个后续可见页面在设计和实现前都要建立“业务能力与 UX 设计溯源表”：

| 用户任务或业务能力 | 现有业务来源 | 必须保持的语义、结果与安全边界 | 新 Vue 呈现与操作设计 | UX 调整理由 | 业务差异及用户决定 | 验证方式 |
|---|---|---|---|---|---|---|
| 开工时逐项填写 | Streamlit、服务、数据库契约或测试 | 明确不可丢失或改义的内容 | 允许重新设计 | 说明效率、清晰度或可访问性依据 | 仅业务边界变化时必填 | 自动检查、浏览器证据与用户验收 |

没有来源的业务能力、数据语义或业务结果不得实现；服务于已有能力的新布局和控件不因旧 UI 没有同形元素而被删除。

## 4. 门槛内容

### 4.1 文档与参考资产重置

- 将 `docs/ui/STYLE.md` 收敛为纯视觉规范，移除固定导航、页面内容、业务状态、操作、快捷键和流程定义；
- 移除 7 张完整 AI 概念图及其活动引用；Git 历史继续保留其来历，但它们不再属于当前设计输入；
- `docs/ui/references/` 只允许保存裁去功能语义的局部视觉片段，并为每个片段声明可借鉴的视觉维度；
- 校正 Master Plan、Phase 2 map、Index 和架构事实中的设计权威与阻断关系；
- 历史 P2-02 至 P2-08 设计稿、即时计划和验收清单不改写，用于保留当时为什么这样实现、当时验收了什么的证据。

### 4.2 现有功能盘点

- 以当前 Streamlit 页面、现有服务、API 契约和测试建立业务任务与结果清单，不把旧页面结构直接当清单结构；
- 区分“必须保留的业务能力与语义”“业务不变但 UX 重新设计”“用户明确要求改变的业务”“旧原型局限”和“概念图臆造业务”；
- 导航由真实用户任务、信息关系和操作效率重新分组，不要求与旧导航一一对应，也不能由 7 项导航模板或未来占位项反推；
- 不把“尚未实现但计划未来开发”伪装成当前入口。

### 4.3 阅卷样板页修正

- 默认主流程支持“按题号批量复核”这一真实教师任务，保持一次比较和处理同一题多份答卷的业务能力；新页面不要求复刻 Streamlit 的原布局和点击顺序；
- P2-05 至 P2-08 的队列、证据查看器、评分检查器和安全确认能力优先复用；
- 单份记录详情降为可选详情或异常深查入口，不作为唯一或默认阅卷模式；现有三栏只是可复用原型，不固定详情页最终布局；
- 批量主视图和可选详情之间如何进入、返回、保存与继续处理，应以任务效率和上下文连续性重新设计，同时保持评分结果、安全确认和失败恢复语义；
- 不在本门槛中改变评分规则、后端契约、数据库、模型调用或真实业务数据。

### 4.4 用户确认

校正后的业务能力与 UX 设计溯源表、导航分组和阅卷主流程先由用户审阅。页面实现完成并通过自动检查后，才按 `docs/user-testing/PHASE2_FRONTEND_RECALIBRATION_TEST_TEMPLATE.md` 生成 `docs/user-testing/checkpoints/phase-2-frontend-source-recalibration-<YYYY-MM-DD>.md`；不得提前编写操作步骤，也不得复用 P2-08 的旧清单。

该清单必须记录：用户实际测试的已复审 40 位 SHA、数据来源、启动方式、地址、可见标识、关闭方式、真实两库测试前后指纹、逐步结果、Blocker/Major、用户原始反馈和用户明确结论。验收既检查业务能力、结果和安全边界没有丢失，也检查新设计是否比旧原型更清楚、高效且容易恢复；不按旧页面逐屏或逐点击判定一致。只有 Blocker/Major 清零且用户明确标记 `passed` 才满足本门槛。结果块使用“门槛”而不是正式包 ID，因此不产生正式包交接块、不进入夜间矩阵，也不改变包计数。

### 4.5 权威文档同步

规格批准后，至少同步 `AGENTS.md`、执行包 README、Phase 2 map、Master Plan、`STYLE.md`、`ARCHITECTURE.md`、`frontend/README.md` 和专用用户验收模板。同步时统一使用“业务能力与结果等价、UX 主动重设计”的口径；历史 P2-02 至 P2-08 规格、计划和验收记录继续原样保存。

## 5. 通过条件

门槛只有同时满足以下条件才算通过：

1. 活动文档中不再把完整 AI 概念图当作页面或功能依据；
2. `STYLE.md` 不再定义导航、页面字段、业务动作、状态机、快捷键或工作流；
3. 后续 Phase 2 页面都使用业务能力与 UX 设计分层的溯源规则；
4. 权威文档明确旧 Streamlit 和既有 Vue 页面不是布局或交互模板，不要求逐屏、逐控件或逐点击复刻；
5. 当前真实阅卷业务盘点完成，按题号批量复核被确认为默认主流程，并形成有设计理由的新 Vue 呈现；
6. 单份详情能力被定位为可选详情，其最终布局由真实任务决定，并完成必要的前端修正；
7. 自动验证、规定桌面视口、错误恢复和必要业务能力覆盖检查通过；
8. 专用版本化清单同时验证业务等价与 UX 改善，并记录已复审 SHA、Blocker/Major 清零和用户明确 `passed`。

门槛通过前，Index 只能记录“未通过”；不能因为 P2-08 已合并、Phase 1 总门槛通过或某个后续包具备技术依赖而绕过。

## 6. 不修改范围

- 不撤销、篡改或重写 P2-08 的合并历史和当时验收证据；
- 当前文档与参考资产重置提交不修改前端源码；门槛后续的前端修正必须在本规格获批后另写即时实施计划；
- 不新增正式执行包编号，不改变 87 包统计或夜间资格矩阵；
- 不修改评分语义、API、Schema、模型配置或真实 `user_data/`；
- 不立即制作新的 AI 全页效果图；确有需要时只制作去语义的局部视觉片段。

## 7. 回退与历史说明

文档和参考资产重置可通过单个 Git 提交回退。被移除的完整概念图仍可从 Git 历史取回用于审计，但不得在回退之外重新加入活动参考集。P2-08 代码继续保留，但组件复用只是实现偏好，不能凌驾于已批准的 UX 重设计。现有组件能够支持新信息架构和任务效率时优先复用；若妨碍信息架构、清晰度、可访问性、上下文连续性、错误恢复或批量处理效率，可在即时实现计划说明理由后重构或替换，并提供测试与可验证回退。
