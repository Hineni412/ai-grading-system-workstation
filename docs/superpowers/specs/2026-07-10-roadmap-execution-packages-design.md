> **适用范围：** Phase 1 至 Phase 5 正式路线；Phase 6 延后
> **依据：** `AGENTS.md`、`ARCHITECTURE.md`、2026-07-03 Master Plan、当前工作区代码与测试审计

## 1. 已确认决策

1. 采用双层路线图：Master Plan 保留方向、依赖和阶段门槛；Execution Package 文档承载可执行的小任务。
2. Phase 1、2、3、4、5 都是确定要做的正式路线。
3. Phase 5 必须实施，但先经过工作流设计、技术实验和评估，再冻结数据模型与产品契约。
4. Phase 6 暂缓，不生成活跃实现包；只记录重启条件、数据红线和前置决策。
5. 跨阶段规划默认使用 GPT-5.6 Sol + Extra High；多数边界清楚的实现使用 GPT-5.6 Terra + Medium/High。
6. 每个执行包条目必须在固定字段中写明规划模型、执行模型、推理强度、升级模型条件和复核模型。
7. 本次只改规划文档，不改业务代码，不改 `user_data/`，不自动提交 Git。

## 2. 为什么不一次生成几十份精确代码计划

未来阶段依赖当前阶段产生的真实接口、文件和类型。如果现在为 Phase 3 至 Phase 5 写死函数签名、行号和测试代码，这些内容会在 Phase 1、2 完成后大面积失效，反而会误导执行模型。

因此采用两级执行资料：

- **执行包地图：** 现在由 Sol + Extra High 一次性生成，覆盖 Phase 1 至 Phase 5 的全部小任务，固定目标、边界、依赖、验收、风险和推荐模型。
- **实现计划：** 每个执行包开始前，基于当时代码生成一份 TDD task-by-task 计划，写明准确文件、接口、测试代码和命令，再交给 Terra 或 Sol 执行。

这样既能提前看清全部工作量和模型预算，又避免把未来代码结构猜成事实。

```text
└── plans/
    └── YYYY-MM-DD-<package-id>-implementation.md
```

职责边界：

- `Master Plan`：解释为什么做、阶段顺序和最终目标，不承载实时进度。
- `EXECUTION_INDEX.md`：唯一进度总表，记录状态、依赖、模型、证据和下一包。
- `phase-*-execution-packages.md`：定义该阶段所有执行包，不写容易漂移的源码行号。
- `plans/*-implementation.md`：单个执行包的临时代码级实施说明，随代码现状生成。
- `AGENTS.md`：只保留当前阶段、当前包、最新验证和数据安全提醒。
- `ARCHITECTURE.md`：只记录已经实现并核验的架构事实，不记录未实施方案。

## 4. 执行包粒度

一个执行包必须满足：

1. 能在一个独立 Codex 任务中调查、实现、验证和交接。
2. 只包含一个主要行为变化或一个可独立验收的迁移步骤。
3. 有明确的“不修改范围”，避免顺手重构。
4. 有独立测试周期，审阅者可以单独接受或拒绝。
5. 涉及数据库、删除、并发、任务取消、模型调用或真实数据时单独成包。
6. 前端页面按可独立验收的用户流程拆分，不按 `components/api/store` 技术层横切成无法运行的半成品。

每个执行包固定包含以下字段：

| 字段 | 含义 |
|---|---|
| ID / 名称 | 稳定编号，如 `P1-07` |
| 状态 | `planned/ready/in_progress/implemented_uncommitted/verified/merged/deferred/blocked` |
| 目标 | 一句话说明可观察结果 |
| 依赖 | 必须先达到的包或阶段门槛 |
| 范围 | 本包要改的行为和主要模块 |
| 不修改 | 明确禁止扩散的领域 |
| 子任务 | 调查、RED、GREEN、回归、文档、交接 |
| 验收 | 精确测试、人工流程、性能或迁移证据 |
| 回退 | 撤销代码、迁移或功能开关的方法 |
| 数据风险 | 是否接触真实库、学生数据、答卷或模型密钥 |
| 规划模型 | 通常为 Sol + Extra High |
| 执行模型 | Terra、Sol 或 Luna 及推理强度 |
| 升级条件 | Terra 遇到何种情况必须停下并切到 Sol |
| 复核模型 | 普通包 Terra High；高风险包 Sol High/Extra High |

## 5. 状态口径

- `implemented_uncommitted`：代码和测试已在本地完成，但还没有形成 Git 检查点。
- `verified`：当前工作区测试通过，但仍未代表已合并。
- `merged`：代码已进入主线或用户指定集成分支，才可以在阶段进度中记为完成。
- `deferred`：用户明确延后，不算阻塞，也不进入近期模型预算。
- `blocked`：存在明确外部依赖，且当前无法继续。

现有 WP1.2 Batch A-E 与最小 JobManager 应标记为 `implemented_uncommitted` 或 `verified`，不能笼统写成 WP1.2/WP1.3 已完成。

## 6. 模型分工

> **模型建议核验日期：** 2026-07-10。执行时若模型选择器已更新，优先保持“旗舰深度规划 / 均衡日常执行 / 低成本机械任务”三档角色不变，再选择当时官方对应模型；不要为了遵守旧名称而使用已弃用模型。

| 工作类型 | 默认模型 | 推理强度 | 原因 |
|---|---|---|---|
| 全路线拆解、依赖审计、阶段门槛 | GPT-5.6 Sol | Extra High | 需要跨模块判断和长期一致性 |
| 普通 API、schema、服务适配、页面迁移 | GPT-5.6 Terra | Medium | 目标明确，兼顾效果、速度和使用成本 |
| 跨模块实现、复杂测试、性能优化 | GPT-5.6 Terra | High | 需要更多调查和验证，但通常不必使用 Sol |
| Schema 迁移、并发、取消、LLM Gateway、删除 | GPT-5.6 Sol | High 或 Extra High | 失败代价高，依赖和回退复杂 |
| 机械性文档同步、清单、批量小改 | GPT-5.6 Luna | Light 或 Medium | 输入输出清楚，可低成本完成 |
| 高风险代码复核与阶段验收 | GPT-5.6 Sol | High | 独立检查遗漏、回归和数据风险 |

模型升级规则：

1. Terra 发现计划与代码事实不符时停止实现，先更新计划；不得自行猜接口。
2. 出现数据库迁移、跨线程状态、不可逆文件操作、评分规则变化或敏感数据边界时升级到 Sol。
3. 同一个执行包连续两次修复失败时停止叠加补丁，切换 Sol 做根因或架构复核。
4. Max/Ultra 不作为默认配置；只有可明确拆成多个独立调查面的阶段审计才考虑 Ultra。

## 7. 阶段范围与门槛

### Phase 1：当前活跃阶段

先增加“Phase 1 稳定化”包，处理当前审计发现的网络盘路径异常、JobManager 取消语义、jobs Schema 双源、复核查询/事务、文件下载闭环和未提交检查点。之后完成剩余领域 API、长任务、LLM Gateway、数据库测量及 API E2E。

Phase 2 样板页不必等待所有题库、图谱和运维端点完成；当复核所需 API、图片端点、JobManager 生命周期和复核 E2E 达到门槛后即可开始，以尽早验证前后端契约。Phase 1 的其他执行包继续完成，整个 Phase 1 仍需在正式前端扩散前通过总验收。

### Phase 2：正式范围

按“工程基础 -> 单题复核样板页 -> 考试与批改主流程 -> 分析与题库训练 -> 切换退役”执行。样板页通过真实浏览器、业务流程和规定视口验收前，不迁移其他复杂页面。

### Phase 3：正式范围

在新前端主流程稳定后进行后端解耦、仓储拆分、SessionManager 拆分、Schema 收敛、字段治理、死代码分批删除和基于测量的性能优化。每个删除批次独立回退。

### Phase 4：正式范围

先建立业务口径、样本数据和可比较评估，再实施标签关系、图谱 2.0、掌握度 v2 和训练结果回流。任何新掌握度公式必须保留旧口径对照和功能开关。

### Phase 5：确定实施，但先实验

Phase 5 从三个实验包开始：教师命题工作流访谈/设计、富文本编辑与预览技术实验、相似题与 AI 评审评估集。只有实验结果达到预设门槛，才冻结 `authored_questions` 状态机、AI 评审契约和发布题库事务。

### Phase 6：延后

仅保留重启条件和不可取消的数据红线。未收到用户重新启用指令前，不创建数据库、不写 API、不开发 UI，也不消耗详细实现规划预算。

## 8. 质量门槛

所有执行包共同遵守：

1. 先测试失败，再做最小实现，再跑定向和回归测试。
2. 小包至少运行相关测试和 `tools/smoke_check.py --skip-tests`。
3. 阶段门槛运行完整 `tools/smoke_check.py`；已知失败必须有根因、归属和处理决定。
4. 数据库变更必须包含迁移、副本预演、`integrity_check`、行数/Schema 对比和回退说明。
5. 前端包必须包含真实浏览器验证、规定视口、加载/空/错/禁用状态和关键业务路径。
6. 不读取、修改或提交真实 `user_data/`，除非用户明确授权该次操作。
7. 每次 Git 检查点都要显式排除 `user_data/`、备份、报告、图片和密钥。

## 9. 生成与执行流程

1. Sol + Extra High 生成并复核 Phase 1 至 Phase 5 执行包地图。
2. 用户从 `EXECUTION_INDEX.md` 选择下一个 `ready` 包。
3. 执行前重新读取代码，由推荐规划模型生成精确 TDD 实现计划。
4. 推荐执行模型按计划实现；发现升级条件立即停止并切换模型。
5. 跑定向测试、回归、冒烟及人工验收。
6. 高风险包由 Sol 做独立复核；普通包由 Terra High 复核。
7. 用户确认后提交、推送或创建 PR，再把状态改为 `merged`。
