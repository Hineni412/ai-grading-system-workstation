# 项目文档治理设计

> **日期：** 2026-07-11
> **状态：** 用户已批准书面规格；PR A 交接协议已合并，未完成的 UAT 运行环境已按用户授权放弃并删除，PR B 可以实施
> **范围：** 项目文档权威分层、历史文档删除、用户说明修正、文档一致性守卫、integration 通道恢复和并行开工门
> **不包含：** 业务功能实现、数据库迁移、真实 `user_data/` 操作、P1-16/P2-01 实现

## 1. 背景与问题

仓库主线当前有约 60 份 Markdown，其中包含 24 份计划、15 份规格和 12 份执行包文档。文档链接整体有效，逐字重复也不是主要问题；真正风险是同一事实由多份文档重复维护，导致当前状态、历史证据、目标架构和用户操作口径互相污染。

本次审计确认的代表性问题包括：

1. `ARCHITECTURE.md` 顶部仍把 P1-02 至 P1-15 描述为尚未合并，但入口和执行索引已经记录 PR #2 合并完成。
2. `EXECUTION_INDEX.md` 要求并行 P1-16 与 P2-01，但 P2-01 在 Phase map 和夜间矩阵中仍为 `planned`，且当前队列只列 P1-16。
3. 并行手册把 integration 描述为干净通道，实际该 worktree 有 9 个独有提交和 2 个未提交修改。
4. 工作机 README 同时出现错误的 `run.bat`/系统 Python 安装指令与正确的便携 `运行.bat` 指令。
5. 私人便携 README 仍使用旧统一技能和“相近补入”口径，与当前精确 `knowledge_point`、不足即缺题的业务规则冲突。
6. 已放弃的细粒度知识图谱规格仍声称已确认并具备实施计划；多个已完成计划仍保留未勾选任务。
7. 存储策略记录了工具并不支持的 `--apply` 参数。
8. `STYLE.md` 和 Master Plan 对主强调色维护了两套值。

## 2. 目标与非目标

### 2.1 目标

1. 为每类事实指定唯一权威文件，消除可变状态的重复维护。
2. 把当前实现、当前队列、稳定包定义、长期战略和专项规则分层。
3. 提炼仍有效结论后，直接删除旧计划、旧审计、被取代或放弃的规格；长期追溯依赖 Git 与 PR，不建立 `docs/archive/`。
4. 修正会误导用户启动、维护、训练推荐或数据操作的说明。
5. 增加只读文档检查，在提交和快速冒烟阶段阻止已知漂移模式复发。
6. 在不丢失现有在途工作的前提下恢复 integration 的单一职责。
7. 定义 P1-16 与 P2-01 可以安全并行的明确门槛。

### 2.2 非目标

- 不把 87 个包重构为 YAML/JSON 生成系统。
- 不改变评分、题号、标签、状态或训练推荐业务语义。
- 不修改生产启动行为或数据库 Schema。
- 不清理真实文件、备份、答卷、报告或数据库。
- 不在本治理包中启动 P1-16、P2-01 或其他业务包。

## 3. 文档权威架构

### 3.1 冲突优先级

发生冲突时固定采用：

1. 用户当前明确指令。
2. 根目录 `AGENTS.md`。
3. `ARCHITECTURE.md` 已实现并核验事实。
4. `EXECUTION_INDEX.md` 实时阶段、包状态、队列和下一动作。
5. 对应 Phase map 的稳定包定义。
6. Master Plan 的长期战略和阶段依赖。

Git 历史、旧 PR 和被删除文档只用于追溯，不得覆盖当前权威文件。

### 3.2 文件职责

| 文档层 | 唯一职责 | 明确排除 |
|---|---|---|
| `AGENTS.md` | AI 接手规则、数据红线、必读顺序、Git 授权与开工门 | 测试数字、PR 流水、逐包完成摘要、worktree 实时状态 |
| `ARCHITECTURE.md` | 当前实现、接口、数据、运行、安全和已知风险 | 分支状态、下一执行包、逐日实施日志 |
| `EXECUTION_INDEX.md` | 唯一实时状态：阶段、包状态、当前队列、下一动作 | 包的源码级实现细节 |
| Phase maps | 稳定目标、依赖、范围、验收、风险和模型 | 可变化的当前状态 |
| Master Plan | 长期方向、阶段依赖、已确认战略决策 | 当前提交号、测试数字、worktree 和即时进度 |
| 专项权威文档 | STYLE、夜间资格、夜间自动化、持久 Git/worktree 规则、用户操作 | 其他层的动态状态或实现流水 |

`CLAUDE.md` 继续作为兼容指针保留，不承载独立规则。

### 3.3 动态状态规则

- 包的 `planned/ready/in_progress/verified/merged` 只在 `EXECUTION_INDEX.md` 维护。
- Phase maps 用“依赖”替代“状态/依赖”字段。
- 夜间资格矩阵只记录稳定风险分类、执行模型和额外门槛，不复制包状态。
- 并行手册只记录持久纪律和现场核验命令，不保存“当前 HEAD”“当前干净”等会失效快照。
- 每次开工必须现场读取 `origin/main`、worktree、分支、未提交状态、`user_data` 和目标文件冲突。

## 4. 历史删除策略

### 4.1 删除原则

删除前只迁移当前仍有效的约束、决策、风险和操作说明。已经被代码、测试、Architecture、Master、Phase maps 或专项权威文档表达的历史步骤不再复制。

删除后：

- 不创建 `docs/archive/`。
- 不保留重定向 stub。
- 通过 Git log、对应提交和 PR 恢复历史原文。
- 当前入口不得再链接被删除文件。

### 4.2 计划删除范围

1. `docs/superpowers/plans/` 中除 Master Plan、本次活动治理计划和仍在执行的即时计划外的完成计划。
2. 治理开始时已完成、被取代或放弃的旧 `docs/superpowers/specs/`；本规格在治理完成前保留。
3. `docs/superpowers/packages/PLAN_AUDIT_2026-07-10.md`。
4. `docs/maintenance/code-ownership-map.md`。
5. `docs/knowledge-practice-operations.md`，其有效用户操作内容并入工作机 README。
6. `ARCHITECTURE.md` 的逐日更新日志、`AGENTS.md` 的逐包完成流水和并行手册的历史清理事故记录。
7. PR A 合并后已经完成的昼夜交接设计/计划，以及已经明确放弃的 UAT 运行环境设计/计划；仍在使用的 `docs/user-testing/README.md`、模板和有效验收清单保留，但不得声称尚未实现的隔离启动器、专用端口或页面横幅已经存在。

删除目标不是追求固定数量。预计活动 Markdown 收敛到约 22 至 25 份；任何仍承担独立活动职责的文件不得为了数量被删除。

## 5. 权威文档修正

### 5.1 工程入口与架构

- `AGENTS.md` 只保留长期项目事实、数据红线、必读入口、Git/worktree 规则和下一动作的 Index 链接。
- `ARCHITECTURE.md` 更新为最新主线事实，修正 P1 合并基线和 FastAPI 运行视图；移除当前分支、下一包和逐日测试流水。
- Architecture 仍保留必须长期解释的用户确认约束、真实数据例外和当前风险，但不重复每包验收数字。

### 5.2 路线与状态

- `EXECUTION_INDEX.md` 同时列出 P1-16 与 P2-01，并成为两包状态的唯一来源。
- Phase maps 删除动态状态值；包依赖、目标、验收和模型保持不变。
- 夜间资格矩阵删除状态列，普通进度不再要求修改矩阵。
- Master Plan 删除“当前进度”段、具体提交 SHA 和易失测试统计；战略决策 D1-D9 与阶段依赖继续保留。

### 5.3 并行与夜间规则

- 并行手册删除 worktree 清单、分支删除历史和 runtime 恢复事故，只保留一包一分支、文件所有权、集成纪律、数据守卫和现场检查命令。
- 夜间自动化继续动态读取任务、Git、Index、矩阵和即时计划，不依赖文档快照。
- 夜间矩阵保留 `eligible_after_plan/daytime_only/completed_not_applicable`，但“是否 ready”只查 Index。
- 用户验收仍保留提交证据和结果等级规则；具体运行环境、数据准备、地址和可见标识必须由对应执行包的已验证清单定义，通用文档不得预设专用 UAT runtime 已实现。

### 5.4 用户与维护文档

- 工作机 README 统一使用 `运行.bat` 和便携 `runtime\python\python.exe`，不再要求系统 Python 或首次联网安装。
- 把有效的精确 `knowledge_point` 训练说明并入工作机 README；删除旧技能目录切换、AI 消歧和 `set-mode skill` 操作指导。
- 私人便携 README 删除“统一技能”“相近补入”和旧管理员页面描述，只保留启动、数据、密钥和继续开发说明。
- `storage-policy.md` 使用实际支持的 `--apply-hardlinks`、`--apply-archives`，并规定任何 apply 都需要用户对该次真实数据操作单独授权。
- `STYLE.md` 接收 D8 的最终 Token：`--color-accent: #2563EB`、`--color-accent-hover: #1D4ED8`、`--color-accent-subtle: #EFF6FF`；Master 只链接 STYLE，不再保存颜色区间。

## 6. integration 通道恢复

### 6.1 当前在途工作

治理设计时，`.worktrees/p1-integration-verification` 比 `origin/main` 超前 9 个提交，并有 `tests/test_handoff_status.py`、`tools/handoff_status.py` 两个未提交修改。这批内容属于昼夜交接/用户验收支撑，不符合“integration 只做集成”的长期职责。随后交接协议及验证器通过 PR #9 进入主线，integration 已恢复到最新 `origin/main`；继续扩展的 UAT runtime 分支因超出当前范围且复审存在重要问题，已经用户明确授权删除，未进入主线。

### 6.2 前置处理

1. 冻结该 worktree，不在其中开始文档治理。
2. 记录完整提交链、未提交差异、`user_data` 状态、分支关系和计划状态。
3. 优先完成原支撑计划的测试、复审和数据守卫，通过独立 PR 合并主线。
4. 如果短期无法完成，则把完整提交链和未提交工作无损迁到专属功能分支/worktree；迁移方案必须先证明不会丢失提交或本地修改。
5. 只有在途成果已妥善保存、对应提交已进入 `origin/main` 或转移完成，integration 才能回到最新共同基线。

禁止使用 `reset --hard`、force push、丢弃独有提交或包含 `user_data` 的 stash。PR A 不夹带本治理的文档删改。

## 7. 防复发检查

新增只读 `tools/check_documentation.py` 及 `tests/test_documentation_governance.py`。工具不得打开 SQLite、写报告或修改任何文件。

检查至少覆盖：

1. Markdown 链接、本地文件引用和用户说明中的启动文件存在。
2. 当前用户文档禁止出现 `run.bat`、`相近补入`、旧 `set-mode --mode skill` 等失效指令。
3. Index 是唯一动态包状态来源；Phase maps 和资格矩阵不维护动态状态。
4. 87 个正式包 ID 唯一、连续、无遗漏；8 个历史完成 ID 只保留汇总口径。
5. Phase maps 与资格矩阵的包标题、执行模型和资格记录一致。
6. 并行手册不包含硬编码 HEAD、当前分支干净声明或过期 worktree 清单。
7. 活动实现计划包含必需字段且没有未完成占位标记；完成计划退出活动入口并按生命周期删除。
8. 被删除文件没有剩余活动引用。

文档检查接入快速冒烟，失败时返回非零退出码并给出文件、行号和稳定错误代码。

## 8. 实施与集成

### 8.1 PR A：恢复 integration（已完成）

- 昼夜交接协议、验证器和通用验收证据规则已经独立合并 `main`。
- integration 已回到最新 `origin/main` 且源码、`user_data` 均干净。
- 未完成的专用 UAT runtime 没有进入主线；其工作树、分支及 8 个独有提交已按用户授权删除。
- PR B 必须删除该 UAT runtime 的计划性承诺，并把通用用户验收说明改为只描述现有能力。

### 8.2 PR B：文档治理

PR A 完成后，从最新主线创建专属 `codex/document-governance` 功能分支。PR B 按四个可独立复核的提交实施：

1. 先写文档治理测试，确认当前已知问题产生 RED。
2. 修正权威文档和状态所有权，使守卫逐步转绿。
3. 修正用户文档、迁移仍有效规则并删除历史文件。
4. 运行最终验证并记录文档数量、复审结果和真实数据指纹。

本规格和实现计划可以在 PR A 前于隔离规划分支准备，但 PR B 的实际删改必须在 PR A 合并并同步后重新校验计划基线。

## 9. 验证与回退

### 9.1 验证门槛

- 文档治理聚焦测试通过。
- Markdown 链接和活动本地引用全部有效。
- 失效启动名、旧技能推荐和过期危险命令在活动用户文档零命中。
- 包 ID、模型、资格和状态所有权检查通过。
- `git diff --check` 通过。
- 完整 `tools/smoke_check.py` 通过。
- 变更前后根目录真实两库大小、UTC 修改时间和 SHA-256 完全一致。
- 提交范围不含 `user_data/`、缓存、临时数据库、截图或构建产物。
- 独立复审为 0 Critical / 0 Important。

### 9.2 回退

- PR A 与 PR B 独立，可分别回退。
- PR B 可整体 revert；被删除文档可从 Git 历史恢复。
- 文档检查工具独立提交，若误报可单独回退，不影响生产应用。
- 治理不执行迁移、真实数据清理或不可逆资产操作。

## 10. 并行开工门

PR B 合并并同步后，只有以下条件全部满足才并行启动 P1-16 与 P2-01：

1. integration 干净且只承担集成职责。
2. 两个功能 worktree 从同一最新 `origin/main` 创建或快进，源码和 `user_data` 状态干净，无指向外部的危险 reparse point。
3. Index 唯一标记 P1-16、P2-01 为 `ready`。
4. 两包分别有 S-XH 生成并复核的源码级即时计划，计划基线是同一最新主线。
5. 计划目标文件无重叠：P1-16 限于题库轻写/导入准备；P2-01 限于 `frontend/` 工程、锁文件和质量命令。
6. P1-16 不扩散到 P1-18 长导入/AI；P2-01 不开始视觉页面或 P2-02/P2-04。
7. 两包完成后逐包进入 integration，执行聚焦回归、前端质量命令、完整 smoke 和真实数据指纹守卫，再通过 PR 合并主线。

满足上述门槛后，项目采用两个实现通道加一个集成通道并行推进；文档治理完成本身不替代即时计划、现场 Git 核验或用户验收门。
