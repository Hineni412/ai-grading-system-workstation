# 用户沟通与逐包模型建议清理设计

## 目标

1. 在项目长期协作规则中明确：用户没有编程基础，Codex 的交付说明应优先帮助用户理解结果和下一步，而不是展示内部技术过程。
2. 删除针对各个执行包或小任务的 Codex 模型选择建议，避免用户需要理解或选择 Sol、Terra、Luna 及其推理档位。
3. 保留夜间自动化实际运行所必需的模型配置和放行规则，确保现有无人值守流程不被破坏。

## 用户沟通规则

在 `AGENTS.md` 增加长期有效的“面向用户的沟通”规则：

- 默认用户没有编程基础。
- 交付时先说明结果、对用户的影响、用户是否需要操作以及下一步选择。
- 不把文件清单、代码实现、命令、测试明细、Git 流程和内部状态作为默认交付主体；只有它们会影响用户判断或用户明确要求时才展开。
- 不可避免的技术术语在第一次出现时用通俗语言解释；适合时使用生活化比喻，例如把数据库迁移解释为“搬家前先清点、备份，再按清单搬到新柜子”。
- 安全风险、数据影响、失败原因和需要用户决定的事项不能为了简化而省略，但要用用户能据此作决定的语言表达。

同步调整面向用户验收与交付的文档，使其与上述规则一致，但不降低技术验证和安全门槛。

## 删除范围

删除以下逐包或逐任务模型建议：

- `EXECUTION_INDEX.md` 当前队列中的“规划/执行/复核模型”列。
- Phase 1 至 Phase 5 地图中每个执行包的 `模型` 行。
- Phase 6 延后文档中未来包的推荐模型。
- packages README 中模型代码、模型分配比例、逐包选模和模型升档建议。
- Master Plan 中 Sol、Terra、Luna 的任务分工建议。
- 夜间资格矩阵中的“执行模型”列，以及只用于说明该包应由哪个模型执行的措辞。

删除后，包的范围、依赖、风险、验收、日夜资格和安全停机条件必须保持不变。

## 保留范围

- `NIGHTLY_AUTOMATION.md` 中自动化已经配置的实际模型、计划放行字段和无人值守执行门槛。
- packages README 中为了与夜间自动化格式兼容而必须保留的放行字段说明；这些字段不再作为日常小任务的模型建议。
- 业务代码和架构文档中的“评分模型”“复核模型”“数据模型”“Pydantic 模型”等产品或代码概念。
- 与 AI 调用安全、真实模型禁用、模型输入隐私和供应商兼容有关的业务规则。

## 一致性处理

- 修改 packages README 和 Index 的文档职责描述，移除“模型代码”“模型选择”等表述。
- 夜间资格矩阵的安全理由改为按风险表达，例如“涉及迁移和真实数据，只允许白天人工监督”，不再写“Sol 执行”。
- 保留 `eligible_after_plan`、`daytime_only` 等资格，因为它们决定能否无人值守运行，而不是推荐用户选择模型。
- 全仓检索 `S-XH`、`S-H`、`T-H`、`T-M`、`L-M`、Sol、Terra、Luna；逐项区分“逐包建议”和“自动化实际配置”，防止误删。

## 验证

完成修改后检查：

1. Phase maps 不再含逐包 `模型` 行。
2. Index 和资格矩阵不再含逐包模型列。
3. README 和 Master Plan 不再指导小任务选择模型。
4. 夜间自动化配置、放行字段和权威提示词仍完整一致。
5. 用户沟通规则在长期入口中清晰可执行，且不会掩盖安全风险或必须由用户决定的事项。
6. Markdown 表格列数正确，链接与文档职责描述没有失效。

## 非目标

- 不修改业务代码、测试、数据库或 `user_data/`。
- 不改变执行包状态、依赖、排期或验收门槛。
- 不重新设计夜间自动化，也不修改其实际模型配置。
