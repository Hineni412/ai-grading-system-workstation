# 昼夜任务交接与用户验收设计

> **状态：** 设计方向已由用户于 2026-07-11 在对话中确认。
> **范围：** 本设计只定义任务交接、夜间选择和用户验收协议；不改变评分规则、业务状态、数据库 Schema 或现有生产启动行为。

## 1. 目标

本设计解决两个问题：

1. 白天可以按用户想法推进当前任务；夜间能够可靠判断该任务是仍需继续、等待用户，还是已经本地完成并等待集成，再决定是否领取另一个互不影响的小包。
2. 用户无需判断内部代码质量，也能在 P1 阶段结束和 P2 前端迁移期间，通过可重复、可观察、不会污染真实数据的步骤完成业务与视觉验收。

成功标准不是“夜间必须产生提交”，也不是“用户替代自动化测试”。自动化负责代码、契约和数据守卫，用户只确认可观察的业务行为与使用体验。

## 2. 非目标

- 夜间任务不自动生成 Sol 计划、创建或重绑 worktree、集成分支、push、创建或合并 PR。
- 用户不负责判断事务、并发、Schema、安全实现或测试覆盖率。
- 不为尚未实现的页面提前编造具体按钮名称和点击路径。
- 不直接使用、重置或写入根目录真实 `user_data/`。
- 不因为建立验收流程而提前实施 P2 页面或 P5 业务能力。

## 3. 已确认事实

- 当前夜间自动化已经检查 Codex 任务、worktree、资格矩阵、`origin/main` 依赖、Sol 即时计划、文件漂移和真实数据守卫。
- 当前自动化能够安全恢复一个符合条件的原任务，或在另一个预先分配的干净 worktree 中实施一个独立包，但尚无统一的“白天任务已完整完成”证据块。
- P1-28、P1-29、P2-08、P2-20 和 P2-21 已定义阶段验收目标；`docs/ui/STYLE.md` 已定义视觉检查项，但这些内容面向开发者，不能直接作为非专业用户的操作手册。
- 仓库目前没有专门的用户自测入口和逐步清单。
- `path_manager.py` 当前先读取 `config/app_config.yaml` 的 `DATA_DIR`，普通 `AI_GRADING_DATA_DIR` 只在配置缺失时生效。安全验收启动不能假设普通环境变量一定覆盖真实数据目录。

## 4. 总体方案

采用“机器可读交接块 + 两层用户验收手册”：

1. 每个正在执行的源码级即时计划保存唯一的昼夜交接块。
2. 夜间自动化结合交接块、Codex 任务状态、Git 和 worktree 实况做二次验证，不盲信文档中的自报状态。
3. `docs/user-testing/README.md` 保存长期稳定的用户验收入口、角色分工、安全规则和问题反馈方式。
4. 每个需要用户观察的可见批次生成一张短测卡；P1-29、P2-08、P2-20 和 P2-21 生成独立正式验收清单。
5. 日常短测与 P2-08 使用固定、可重置的演示数据；P2-20 才允许在备份后使用用户明确授权的真实考试副本。

## 5. 昼夜交接协议

### 5.1 权威位置

交接块放在当前执行包的源码级即时计划中。一个执行包只能有一个活动即时计划；一旦首次被 Codex 任务领取，该计划必须且只能有一个交接块，聊天摘要、任务标题或提交时间都不能替代该块。

尚未被任何任务领取的 `ready` 候选不是交接状态，继续使用现有 `规划状态`、`规划模型`、`允许夜间执行` 和 `计划基线` 等放行字段，可以暂时没有交接块。自动化只有在任务、分支和 worktree 均证明它从未开工时，才能按新候选规则处理；首次领取时先记录当前全部 stash SHA，再把 `in_progress` 交接块写入即时计划。首次领取后再缺块，或存在提交/脏改动却声称从未开工，均按状态不明处理。

建议格式：

```markdown
<!-- HANDOFF_STATUS_START -->
## 昼夜交接

**执行包：** P1-16
**交接状态：** in_progress
**功能提交：** none
**自动验证：** pending
**独立复审：** pending
**用户验收：** not_required
**真实数据指纹：** not_touched
**Stash 基线：** none
**夜间动作：** report_only
<!-- HANDOFF_STATUS_END -->
```

活动即时计划必须且只能包含一对 `HANDOFF_STATUS_START/END` 标记。自动化先用项目验证器提取和校验标记间字段，再结合 Git 与任务实况决策；不得让模型凭自然语言猜测字段。

正式包即时计划的文件名必须包含小写包号，且交接块之外必须恰好有一个顶部 `**执行包：** P<Phase>-<两位序号>` 字段。文件名、顶部字段和交接块中的包号必须一致，避免复制计划后把一个包的状态误用于另一个包。

该交接块只用于执行索引中的正式 `P<Phase>-<两位序号>` 包。一次性的治理或验收支撑工作不得冒用正式包 ID、改变 87 包计数或进入夜间候选；这类工作只能白天实施和集成，并在被正式包消费前先进入最新 `origin/main`。

字段值必须使用以下枚举：

| 字段 | 允许值 | 含义 |
|---|---|---|
| `执行包` | 对应正式包 ID，例如 `P1-16` | 必须与即时计划头部、分支分配和执行索引唯一对应 |
| `交接状态` | `in_progress`、`resumable`、`waiting_review`、`waiting_user`、`verified_pending_integration` | 当前包是否仍在实施、可恢复、等待复审、等待用户，或已经本地验证完成 |
| `功能提交` | `none`、`branch_head` 或完整 40 位 Git SHA | 等待复审/用户时可用 `branch_head`；最终交接提交记录用户实际验收或复审的最终树锚点 SHA |
| `自动验证` | `pending`、`passed`、`failed` | 即时计划要求的测试和检查是否全部通过 |
| `独立复审` | `pending`、`passed`、`failed` | 当前提交的独立复审结果 |
| `用户验收` | `not_required`、`pending`、`passed`、`failed` | 当前包是否需要以及是否通过用户观察 |
| `真实数据指纹` | `not_touched`、`unchanged`、`changed` | 根目录真实两库是否未接触或经前后比较保持不变 |
| `Stash 基线` | `none` 或领取时已有 stash 的逗号分隔完整 SHA | 区分领取前共享 stash 与领取后新 stash；写入后不可追加 |
| `夜间动作` | `report_only`、`resume_only`、`independent_candidate_allowed` | 夜间对该包允许采取的最高动作 |

### 5.2 状态语义

#### `in_progress`

任务仍在正常工作。对应 worktree 被占用；夜间不得接管或复用。其他通道是否可工作仍按依赖、文件冲突和并行手册判断。

#### `resumable`

任务已停止但下一步明确，不等待用户、不阻塞，且即时计划仍有效。只有同时满足现有夜间资格与安全门槛并且 `夜间动作: resume_only` 时，自动化才能向原任务发送一次继续消息，然后结束本轮。

#### `waiting_review`

实现和自动验证已完成，功能分支已创建一个本地提交，但独立复审或必要用户验收尚未完成。功能提交内的交接块写 `功能提交: branch_head`；自动化从当前分支解析完整 HEAD SHA。该分支保持冻结，夜间不得继续修改；其他通道仍按依赖和冲突规则判断。

#### `waiting_user`

代码或页面正在等待用户选择、授权或验收。夜间不得继续该任务，也不得推测用户结论。该通道保持占用；其他通道只有在不跨越当前用户门槛、不依赖未合并结果且文件无冲突时才可考虑。

独立复审尚未完成时，`功能提交` 只能是 `none` 或 `branch_head`，`独立复审` 保持 `pending`。复审通过后，Codex 创建一个只更新即时计划的 `waiting_user` 锚点提交：它记录直接父提交的完整已复审 SHA，且自动验证与独立复审均为 `passed`。该锚点之后不得再插入源码提交。

用户明确通过后，Codex 紧接锚点提交把结果写入该包自己的版本化验收清单并创建范围受限的证据提交，期间不得改源码；随后立即创建只更新即时计划的最终交接提交。清单机器结果块中的“验收提交”指锚点记录的已复审功能 SHA，最终交接块的 40 位 SHA 则指包含该功能树和验收结果的直接父提交。

#### `verified_pending_integration`

当前包已经完成本地实现、验证、独立复审和必要的用户验收。复审与验收通过后创建一个只更新当前即时计划交接块的文档提交：交接块记录直接父提交的完整 40 位 SHA，并把状态改为 `verified_pending_integration`。该父提交是最终树锚点：通常是功能提交；需要把用户清单结果版本化时，可以是只修改该包验收清单的范围受限证据提交，但其树中的源码必须仍是已经复审和被用户操作的版本。夜间不得再次修改、提交或复用该分支；它可以考察其他独立通道。

`merged` 不作为手工交接状态。是否已集成必须由 Git 验证功能提交已进入最新 `origin/main`，不能依赖计划自报。

### 5.3 字段组合约束

| 交接状态 | 功能提交 | 自动验证 | 独立复审 | 用户验收 | 夜间动作 |
|---|---|---|---|---|---|
| `in_progress` | `none` | `pending` | `pending` | `pending` 或 `not_required` | `report_only` |
| `resumable` | `none` | `pending` 或 `failed` | `pending` | `pending` 或 `not_required` | `resume_only` |
| `waiting_review` | `branch_head` | `passed` | `pending` | `pending` 或 `not_required` | `report_only` |
| `waiting_user` | 复审前为 `none`/`branch_head`；复审通过后为完整 40 位已复审 SHA | 复审前 `pending`/`passed`；复审通过后 `passed` | `pending`，或与完整 SHA 同时为 `passed` | `pending` | `report_only` |
| `verified_pending_integration` | 完整 40 位 SHA | `passed` | `passed` | `passed` 或 `not_required` | `independent_candidate_allowed` |

不符合表中组合的交接块一律视为状态不明。`independent_candidate_allowed` 只表示当前完成分支不阻止自动化考察其他通道，不授权复用当前 worktree，也不跳过其他候选包自身的全部门槛。

前四种状态允许记录 `not_touched`、`unchanged` 或 `changed`，但 `changed` 会覆盖表中的夜间动作并让验证器返回失败，自动化必须立即停止并升级。`verified_pending_integration` 只允许 `not_touched` 或 `unchanged`。

### 5.4 完成本地验证的必要条件

只有以下条件全部满足，才可写入 `verified_pending_integration`：

1. 即时计划任务全部完成，没有未解释的跳过项。
2. 聚焦测试、受影响回归、快速冒烟和适用的前端质量命令全部通过。
3. 独立复审没有未解决的 Critical、Important 或用户要求必须修复的问题。
4. 需要用户验收的包已经得到明确 `passed`；不能用截图自动检查替代用户决定。
5. 根目录真实两库未接触，或大小、UTC 修改时间和 SHA-256 前后完全一致。
6. 已创建范围单一的本地功能提交。需要用户验收时，复审通过后先创建仅修改即时计划的 `waiting_user` 锚点提交，它记录直接父提交的完整已复审 SHA；再创建只更新该包验收清单的证据提交；最后创建一个仅修改当前即时计划的交接提交。
7. 交接块记录的 40 位 SHA 必须是交接提交的直接父提交。`用户验收: passed` 时，该父提交必须只修改 `docs/user-testing/checkpoints/` 下唯一一份以本包号开头的 Markdown 清单；该清单的机器结果块必须记录同一包号、锚点中的已复审 SHA 和 `passed`。证据提交必须直接跟在只改计划的 `waiting_user` 锚点之后，锚点的直接父提交必须等于其记录的已复审 SHA；交接提交不得夹带源码、共享状态文档、验收清单或其他执行包文件。
8. worktree 源码状态干净；`origin/main..HEAD` 整段包提交历史不得新增、修改或删除 `user_data/`，即使后续又恢复也不允许。首次领取时记录当时全部 stash SHA，后续新增 stash 中也不得包含 `user_data/`；主线已有且本包从未触及的历史跟踪文件及领取前已记录的共享 stash 可以保留，任何其他未提交本地数据仍然阻塞。
9. 没有未记录的接口、评分、标签、状态或视觉差异。

自动化必须现场复核这些证据。字段缺失、值不合法、SHA 不存在、功能提交不是交接提交的直接父提交、最新提交还修改了即时计划之外的文件、分支不干净或证据与 Git 实况不一致时，按状态不明处理。

使用 `功能提交: branch_head` 的 `waiting_review`/复审前 `waiting_user`，以及使用完整 SHA 的复审后 `waiting_user`，都必须保持 worktree 干净。完整 SHA 的锚点提交还必须只修改即时计划并指向其直接父提交；否则验证器按失败处理。

夜间 Terra 完成实现时仍只创建一个功能提交，并把状态保留为 `waiting_review`；它不能自行声称独立复审通过。最终交接提交由完成复审和必要用户验收的白天任务创建。

### 5.5 夜间决策顺序

1. 更新 `origin/main` 的只读认知，读取项目入口、资格矩阵、执行索引、并行手册、活动即时计划和 Codex 任务状态。
2. 对已经领取过的包，按任务、分支、worktree 和交接块唯一对应执行包；无法唯一对应时停止。对从未领取的干净 `ready` 候选，只核对现有夜间放行字段。
3. 对运行中、等待复审、等待用户、阻塞或状态不明的任务，只占用其通道，不修改。
4. 若存在唯一可恢复原任务，复核资格、计划基线、数据和冲突后只唤醒该任务，本轮结束。
5. 对 `verified_pending_integration` 分支只核验并报告，保持冻结；未进入 `origin/main` 的提交不能满足其他包依赖。
6. 没有需要恢复的原任务时，才从其他通道选择一个从未领取的 `eligible_after_plan` 包。该包仍须为 `ready`、依赖已合并、已有专属干净 worktree 和 Sol 放行计划，并且不与未集成分支发生文件或契约冲突；开始任何源码修改前先写入 `in_progress` 交接块。
7. 每晚最多实施一个包，只创建本地提交；白天负责 integration、PR 和主线同步。

### 5.6 安全默认值

- 没有交接块：`report_only`。
- 任一字段为 `pending`、`failed` 或非法值：对当前包最多 `report_only`。
- 用户验收为 `pending`：不得恢复需要用户决定的步骤。
- 真实数据指纹为 `changed`：立即停止并升级给用户。
- 交接块声称完成但 Git、测试或任务状态不一致：以更保守的现场证据为准。

## 6. 用户验收体系

### 6.1 文档结构

长期入口：

```text
docs/user-testing/README.md
docs/user-testing/USER_TEST_TEMPLATE.md
docs/user-testing/checkpoints/
```

- `README.md`：用户角色、启动方式、安全边界、测试节奏、反馈格式和如何恢复。
- `USER_TEST_TEMPLATE.md`：供 Codex 在可见批次完成后生成短测卡或正式验收清单。
- `checkpoints/`：只在对应 UI 和流程已经实现后生成具体清单，不提前猜测未来界面。

计划中的正式清单：

| 门槛 | 内容 | 默认数据 | 预计用户时间 |
|---|---|---|---:|
| P1-29 | 当前 Streamlit 业务行为和后端改造后的黑盒基线 | 固定演示数据 | 20-30 分钟 |
| P2-08 | 单题复核样板页、视觉、快捷键和失败保留 | 固定演示数据 | 30-45 分钟 |
| P2-20 | 新 UI 建会话至导出的完整五流程 | 用户授权考试副本 | 60-90 分钟 |
| P2-21 | 新启动入口、刷新、重启、深路由和 Streamlit 回退 | 固定演示数据 | 15-20 分钟 |

### 6.2 验收节奏

- 纯工程或不可见包不要求用户测试，例如 P2-01 工程基础和 P2-04 API Client。
- 每个产生明显可见变化的前端批次完成后，生成一张 5-10 分钟短测卡。
- P2-08 通过前不得扩散复杂页面；P2-20 通过前不得切换默认入口；P2-21 稳定一个验收周期前不得执行 P2-22 删除。
- 同一视觉门槛失败后，回到对应执行包修复，不在验收任务中夹带代码修改。

每个前端即时计划必须显式写明：

```markdown
**用户自测：** none | quick | formal
**自测清单：** <path | not_required>
```

### 6.3 用户与 Codex 分工

Codex 负责：

1. 准备隔离数据、启动本地服务并给出唯一访问地址。
2. 在清单中写出编号步骤、预期结果、停止条件和恢复方式。
3. 运行自动测试、浏览器检查、多视口截图和控制台检查。
4. 根据用户反馈记录通过、失败和证据，更新验收结果。
5. 分析技术日志并提出修复；不要求用户解释堆栈或数据库。

用户负责：

1. 按编号执行操作并观察页面和业务结果。
2. 判断布局、文案、流程、响应和结果是否符合实际使用习惯。
3. 遇到异常时提供“步骤编号 + 看到的现象 + 截图”。
4. 对正式门槛明确给出通过或不通过。

用户不需要编辑 Markdown、运行测试命令或判断内部技术实现。截图若包含学生姓名、答卷或密钥，必须先脱敏；原始截图默认只用于当前对话排查，不纳入 Git。

### 6.4 每张自测清单的固定结构

1. **版本信息：** 执行包、完整提交 SHA、日期、页面范围和预计耗时。
2. **安全说明：** 当前模式、数据来源、真实数据是否隔离、如何重置。
3. **启动信息：** Codex 已执行的启动动作、访问地址、应看到的验收模式标识。
4. **测试前检查：** 浏览器、窗口尺寸、演示账号或会话、已知限制。
5. **编号步骤：** 一步只做一个动作，说明预期页面、数据和状态变化。
6. **失败处理：** 哪些问题应立即停止，哪些可以继续记录。
7. **结果记录：** `pending`、`passed` 或 `failed`，以及失败步骤和证据。
8. **恢复方式：** 关闭服务、重置验收数据和重新开始的方法。

### 6.5 结果等级

| 等级 | 示例 | 门槛处理 |
|---|---|---|
| Blocker | 无法启动、误用真实数据、数据损坏、最终分错误、核心流程无法继续 | 立即停止，门槛失败 |
| Major | 页面重叠导致无法操作、关键状态错误、失败后输入丢失、导出结果不一致 | 门槛失败，回对应包修复 |
| Minor | 不影响操作的间距、颜色或文字细节 | 记录；是否阻塞由用户决定 |

正式验收只有在 Blocker/Major 清零且用户明确确认后才能标记 `passed`。

## 7. 验收数据与启动隔离

### 7.1 日常演示模式

日常短测和 P2-08 使用固定、可重建的演示数据。源数据可以由受控 fixture 和生成器组成，运行时复制到仓库外的专用目录，例如：

```text
%LOCALAPPDATA%/AIGradingSystem/uat/active/
```

每次“重置演示数据”只能删除和重建该受控目录。执行前必须解析绝对路径并确认它位于专用 UAT 根下；路径不符立即停止。

### 7.2 专用验收启动模式

实施阶段应提供独立的用户验收启动入口，并满足：

1. 正常 `运行.bat` 和现有 `config/app_config.yaml` 行为保持不变。
2. 只有显式 `AI_GRADING_UAT_MODE=1` 时才读取 `AI_GRADING_UAT_DATA_DIR`；该变量缺失、无法解析、落入仓库真实 `user_data/` 或不在专用 UAT 根下时拒绝启动。正常模式继续沿用现有配置优先级。
3. 验收模式使用独立端口，并在页面首屏持续显示“用户验收模式”，避免与真实工作环境混淆。
4. 默认不读取真实考试数据，不执行真实 LLM 调用；演示流程使用固定或预生成结果，并把 `AI_GRADING_API_PROFILES_PATH` 指向 UAT 专用空配置。UAT 子进程还必须清除已知密钥环境变量、禁用 legacy profile 迁移并写入独立迁移标记，避免空配置又从旧位置或父进程恢复机器真实密钥。
5. 关闭与重启后继续使用同一 UAT 运行目录，只有用户选择重置时才重建。
6. 启动 UAT 前关闭正常应用并确认专用端口空闲；UAT 进程退出时必须回收全部子进程，并再次比较真实两库指纹。
6. 启动前后记录真实两库指纹，必须完全不变。

专用模式所需的数据根优先级必须有自动测试；不能依赖当前会被 `DATA_DIR` 覆盖的普通环境变量行为。

### 7.3 P2-20 授权副本模式

P2-20 使用用户明确授权的考试副本，不直接打开原始数据：

1. 先记录并备份源数据，复制到独立验收根。
2. 清楚显示副本路径、考试名称和本次允许的模型/网络行为。
3. 任何写入只发生在副本；源数据前后指纹必须一致。
4. 真实模型调用、API key 和网络访问需要单独明确授权；没有授权时使用可重复的模拟路径，不伪称完成真实模型验收。
5. 验收结束后由用户决定保留证据还是删除副本；删除前再次核验目标位于 UAT 根。

任何真实考试副本、未脱敏截图、导出报告和 API key 均不得提交到仓库。正式清单只记录脱敏结论、步骤编号和必要的安全证据。

## 8. 与执行包体系的关系

- `NIGHTLY_AUTOMATION.md`：读取并验证交接块，明确完成分支冻结和其他通道选择规则。
- `NIGHTLY_ELIGIBILITY_MATRIX.md`：继续只判断包的先天夜间资格，不保存瞬时交接状态。
- `README.md`：增加交接字段和用户自测字段的使用说明。
- `PARALLEL_WORKTREE_EXECUTION_2026-07-11.md`：说明完成待集成分支仍占用原通道，但不阻止无依赖、无冲突的其他通道。
- `EXECUTION_INDEX.md`：只维护包状态与主线进度，不复制任务级交接证据。
- P1-29、P2-08、P2-20、P2-21：把对应用户清单作为包的正式产物和验收证据。

## 9. 实施顺序

1. **协议文档：** 增加交接块、用户测试入口和模板，并更新夜间与并行规则。
2. **安全验收运行时：** 在首次用户短测前实现专用 UAT 数据根、重置守卫、启动入口、明显标识和测试。
3. **P1-29 清单：** 根据当时可运行的 Streamlit 与 API 行为生成黑盒基线，不提前写虚构步骤。
4. **P2 可见批次：** 每个可见改动随包生成短测卡，由 Codex 启动页面并交给用户观察。
5. **正式门槛：** P2-08、P2-20、P2-21 分别生成并执行正式清单；失败回到对应功能包。

第一阶段只改变文档和自动化协议。UAT 启动器、fixture 和页面标识进入白天专用的非正式支撑包，采用 TDD 和隔离 worktree 实施，并在 P1-29 前合并；具体正式清单仍由对应正式包按当时可运行界面生成。

## 10. 错误与恢复

- 交接字段与现场证据矛盾：自动化停止并报告，不自动“修正”状态。
- 用户在自测中发现 Blocker/Major：立即停止正式门槛，保留 UAT 副本和必要证据，创建对应修复任务。
- UAT 重置失败：不得回退到真实 `user_data/`；关闭服务并报告绝对路径。
- 页面没有验收模式标识或地址与清单不一致：用户不继续操作。
- 真实数据库指纹变化：停止全部自动动作，保留现场并请求用户决定。

## 11. 验收标准

本设计实施完成后必须证明：

1. 夜间能区分 `resumable`、`waiting_review`、`waiting_user` 和 `verified_pending_integration`，且不会修改等待复审、等待用户或完成待集成分支。
2. 完成待集成的白天任务不阻止另一个预先放行、无依赖、无文件冲突的通道工作。
3. 未进入 `origin/main` 的提交不能满足后续包依赖。
4. 缺字段、非法字段、伪造 SHA、非纯文档交接提交、测试失败、复审待处理、用户待验收或数据指纹异常均安全停机。
5. 用户可以只根据清单和页面完成短测，不需要运行命令或编辑文档。
6. 日常短测可以一键重置固定演示数据，且真实两库指纹不变。
7. P1-29、P2-08、P2-20 和 P2-21 各有版本化正式清单和明确结果。
8. 独立 Sol 复审为 0 Critical / 0 Important；所有文档链接和枚举值通过机械检查。

## 12. 回退

- 协议文档和模板可通过独立文档提交回退，不影响业务代码。
- 夜间自动化提示词回退时必须同步项目权威文本和 Codex automation 配置，并重新做逐字比较。
- UAT 模式必须是附加入口；删除其入口、环境开关和仓库外 UAT 目录即可回退，正常 `运行.bat` 与真实数据路径不受影响。
