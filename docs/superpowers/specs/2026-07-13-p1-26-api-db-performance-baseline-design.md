# P1-26 API/DB 性能测量基线设计

## 1. 目标与边界

P1-26 在任何性能优化之前建立可重复的 API/数据库测量基线。它回答四个问题：一次代表性 API 请求用了多长时间、执行了多少条数据库语句、向调用方返回了多少条记录，以及这些数字对应多大的生成数据集。

本包只测量和报告，不添加缓存、索引、连接池或请求级连接复用，不改变现有 SQL、分页、排序、业务状态、评分规则、标签语义或错误契约。所有样本均由固定随机种子生成并保存在系统临时目录；不读取、复制、打开或写入根目录真实 `user_data/`，不记录学生正文、题目正文、SQL 文本、响应正文、密钥、文件名或内部绝对路径。

P1-26 是不可见工程包，用户自测为 `none`。性能数字是后续 P1-27/P3-18 的决策证据，不是本包的产品 SLA，也不因某个端点较慢而在本包内顺手优化。

## 2. 方案选择

采用“默认关闭的真实请求测量 + 代表性只读端点矩阵 + 可重复生成数据”方案。

没有选择覆盖当前全部写入、任务和媒体操作，因为这些操作需要大量副作用 fixture，会扩大到 P1-23、P1-28 等包，并不能更好回答 P1-27 的数据库连接问题。也不采用只在测试中 monkeypatch `sqlite3.connect` 的方案，因为它无法证明真实 FastAPI 中间件、依赖和服务连接路径的开销与隔离行为。

测量器进入正常请求链，但默认关闭。启用时只保存聚合数字；关闭时不安装 SQLite trace callback，不改变响应，不产生性能报告。基准工具通过显式注入内存 sink 启用测量，不依赖解析日志，也不向公开响应增加性能 header。

## 3. 指标口径

每次请求先形成一条 `RequestPerformanceRecord`，只包含以下安全字段：

- HTTP 方法和 FastAPI 路由模板，例如 `/api/question-bank/questions/{question_id}`，不保存原始 URL、查询词或资源 ID。
- 状态码、总耗时毫秒数和随机生成的请求 ID。
- `db_statements_total`：启用测量后，该请求上下文中所有已接入连接执行的 SQLite 语句数。
- `db_select_statements`：上述语句中首个 SQL token 为 `SELECT` 或 `WITH` 的数量，用于发现可能的 N+1 查询。

基准工具把该请求记录与响应的公开结构合并为 `BenchmarkSample`，再补充：

- `response_records`：由场景针对公开响应结构计算的返回记录数；列表取 `items`、`rows`、`nodes`、`students` 或同类公开集合长度，单对象和二进制成功响应记为 1，空成功响应记为 0。
- 响应字节数、数据档位和生成数据 manifest 的计数摘要。

请求 ID 只用于在内存中把请求记录与当前样本关联，不写入最终 JSON 或 Markdown 报告。

测量器只读取 SQL 的首个 token 做内存分类，绝不保存、输出或哈希完整 SQL。事务控制和 PRAGMA 仍计入 `db_statements_total`，但不计入 `db_select_statements`，这样既能看到连接初始化成本，也能单独比较数据查询形状。

每个场景先执行 3 次不计入结果的预热，再执行 20 次正式样本。报告记录 p50、p95、最小值、最大值；查询数同时记录最小值、中位数和最大值。p95 使用 nearest-rank 定义，20 个样本时取排序后的第 19 个值。计时使用 `time.perf_counter_ns()`，报告统一换算为毫秒。

## 4. 组件与职责

### 4.1 请求测量核心

新增独立的性能测量模块，负责：

- 用 `contextvars` 为每个请求建立隔离 recorder，保证并发请求互不串数。
- 提供 `instrument_sqlite_connection(connection)`；只有当前请求正在测量时才安装 trace callback。
- 在请求结束时形成不可变记录并交给 sink；sink 失败只写安全警告，不覆盖业务响应。
- 提供空 sink 和内存 sink，生产默认使用空 sink且测量关闭。

现有 API 请求中间件继续独占 request ID 和总耗时日志。P1-26 在同一中间件边界内启动/结束 recorder，路由完成后使用 `request.scope["route"].path` 取得模板。404 等未匹配请求使用固定占位模板，不记录原始路径。

### 4.2 SQLite 接入点

只在 P1-26 目标端点实际经过的公共连接边界调用 `instrument_sqlite_connection()`：

- `DBManager._connect()`；
- `question_bank.database.schema.connect()`；
- Question Bank/Graph 稳定临时候选的只读连接；
- Training task 的只读连接；
- Ops 临时候选数据库验证连接。

这些调用不改变连接所有权、事务、row factory、WAL、busy timeout、只读 URI 或关闭顺序。测量关闭时只做一次廉价的上下文检查，不安装 callback。P1-26 不为了覆盖更多语句而重写绕过上述边界的旧代码；未接入连接必须在报告中列为测量覆盖限制。

### 4.3 生成数据与临时运行环境

基准 fixture 使用固定种子生成两套相互匹配的 SQLite 数据和必要文件资产。2026-07-13 用户明确覆盖原设计：原 `large` 工作负载耗时过长，不再运行；其七个计数组件分别取原值的 5%，向上取整并保证为正数，公开名称改为 `large_5pct`。CLI 默认选择 `small`、`medium`、`large_5pct`，旧 `large` 选择器必须校验失败，不能静默映射到较小工作负载。

三个默认档位是命名工作负载，不是按每个维度单调递增的“小/中/大”序列。`large_5pct` 只表示“原大型档的 5% 覆盖版”；它在部分维度小于 `small` 或 `medium`，报告必须展示实际 manifest 计数，不能根据名称推断规模顺序：

| 档位 | 考试 | 学生 | 每场评分题 | 阅卷明细上限 | 题库题目 | 训练任务 | 备份元数据 |
|---|---:|---:|---:|---:|---:|---:|---:|
| small | 1 | 30 | 10 | 300 | 200 | 10 | 5 |
| medium | 5 | 200 | 20 | 20,000 | 2,000 | 100 | 50 |
| large_5pct | 1 | 25 | 2 | 7,500 | 500 | 25 | 5 |

数据生成器显式写入当前服务真正读取的最小列和关系：学生、会话、答卷、结果、逐题明细、题库试卷/题目/当前标签、确认来源链接、训练任务及变体/题目快照。文本字段只使用短固定占位符，不生成真实姓名、学校、题干或答卷内容。媒体场景使用一张小型生成 PNG，并放在临时受控根中。

工具把临时数据根注入独立 FastAPI app，所有写入都在临时目录。每个档位生成后记录数据库大小、表行数和 manifest，但报告只保存逻辑名称与计数，不保存临时路径。

### 4.4 基准场景矩阵

矩阵覆盖 P1-26 直接依赖包中对规模敏感的只读接口：

1. Question Bank：试卷列表、题目默认分页、组合筛选分页、题目详情、一个受控素材和两类预览中的一个可用样本。
2. Training：诊断、推荐预览、训练任务分页和任务详情；不确认任务、不提交导出 Job。
3. Graph：profiles、rows、evidence 三个只读 POST。
4. Ops：self-check 和 backups 两个只读 GET。
5. Control：`/api/healthz`，用于观察不访问业务数据库的请求框架开销。

每个场景使用确定性的合法 ID、scope、过滤器和页大小。题目列表同时测量默认查询与一个组合过滤/排序查询；Graph/Training 使用整个生成档位的 scope，从而暴露查询数是否随学生、明细或题目数量增长。二进制响应只统计状态、字节数和一条返回记录，不保存文件内容。

写 API、长任务、真实媒体、真实模型和真实 Ops 操作明确排除。若实现调查证明某个列出的只读端点不能在不扩张包边界的情况下稳定生成 fixture，计划必须先记录证据并安全停机，不得静默删除场景。

## 5. 结果、N+1 判断与报告

基准工具输出一个版本化 JSON 结果和一份 Markdown 基线报告。两者只包含：

- 包号、代码 SHA、固定种子、运行时间、Windows/Python/SQLite 版本、逻辑 CPU 数；
- 数据档位 manifest；
- 每个场景的样本数、p50/p95/min/max、数据库语句数摘要、SELECT 数摘要、返回记录数和响应字节数；
- 测量覆盖限制、失败场景和可能的 N+1 候选。

不保存主机名、用户名、内部路径、环境变量、完整命令行或业务内容。

“可能的 N+1”只作为观察标签，并且只明确比较 `small` 与 `large_5pct`。只有同一场景的 `scale_driver_count` 从 `small` 到 `large_5pct` 实际增加，且 `db_select_statements` 与返回记录数或输入实体数近似同比增长，才标记候选；驱动量没有正向增幅、查询数固定但耗时增长时都不标记 N+1。`large_5pct` 不代表大于 `medium`，三档整体也不构成单调递增序列。报告不自动建议索引、缓存或连接池，也不把机器间延迟差异解释成回归。

可重复性的硬门槛是：相同代码、种子和场景连续两次运行时，状态码、数据 manifest、返回记录数以及查询数摘要完全一致；耗时只要求为有限非负值并完整产生 p50/p95，不要求两次相等。

## 6. 失败、安全与清理

- 任一正式场景返回非预期状态码、缺少测量记录、样本不足或 JSON schema 无效时，整次基准失败并明确指出逻辑场景，不继续生成“部分成功基线”。
- recorder、trace callback 或 sink 的异常不得改变 API 业务结果；基准工具会把缺失测量视为失败。
- 并发隔离测试必须证明两个请求的查询数不会互相污染，异常请求也会正确释放 contextvar。
- 临时目录由上下文管理器创建和清理；清理失败只报告逻辑临时资源类型，不打印路径。
- 基准开始和结束都只读比较根目录两个真实数据库的大小、UTC 修改时间和 SHA-256，不用 SQLite 打开它们。任何变化立即阻塞交接。
- Git 范围不得包含 `user_data/`、临时数据库、缓存、生成图片、原始逐次 timing dump、日志或真实导出。

## 7. 测试设计

按 TDD 实施以下层次：

1. 测量核心单元测试：默认关闭、SQL token 分类、成功/异常收尾、sink 失败、嵌套与并发 context 隔离、记录字段脱敏。
2. 中间件/API 测试：成功和错误响应都有有限耗时；只记录路由模板；关闭时不产生记录；测量不能改变响应或 request ID。
3. 连接接入测试：临时 grading DB、question-bank `connect()`、稳定快照只读连接、Training 只读连接和 Ops 候选校验都能计数，且原事务/只读/关闭语义不变。
4. 生成器测试：三个 manifest 确定、外键关系有效、重复种子等价、所有路径位于 pytest 临时目录、文本不含真实样本 marker。
5. 基准与报告契约测试：使用缩小的测试档位验证预热排除、20 样本 p50/p95、返回记录计数、失败即停止、JSON/Markdown 不含被禁止字段。
6. 可重复性测试：同一微型档位连续两次的 manifest、状态、查询数和返回记录数一致。

功能分支门槛为 P1-26 聚焦测试、受影响的 API/Question Bank/Training/Graph/Ops 回归、`git diff --check`、`tools/smoke_check.py --skip-tests`、空的 worktree `user_data/` 状态和根目录真实两库指纹不变。P1-26 不改变 Schema 或核心状态机，默认不在功能分支运行全量 pytest；integration 波次末按仓库规则运行完整 smoke。

## 8. 回退与后续

P1-26 不含 Schema 或业务数据迁移。回退时撤销性能模块、连接接入点、生成器、基准工具和报告即可；默认关闭状态保证移除前后业务 API 契约相同。

P1-27 只能引用本报告选择经过测量证明有收益的连接复用候选，并必须独立验证并发、异常关闭、线程隔离与只读拒写。P3-18 的索引、缓存或其他优化同样需要独立的前后对比计划；P1-26 本身不批准任何优化。
