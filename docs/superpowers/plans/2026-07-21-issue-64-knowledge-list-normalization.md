# Issue #64 知识点列表字符串规范化

**状态：** review_passed
**基线：** `44d0ec7dee7eb85b75626699c74167be593558b1`
**关联：** GitHub Issue #64、P2-20 正式验收发现的独立缺陷修复

## 冻结边界

- **目标：** 将模型返回的、可以无歧义解析且一一对应的知识点编号/名称列表字符串，规范化为现有内部知识点结构，解除评分依据的错误保存阻断。
- **包含：**
  - 只安全解析非空的列表或元组文本；
  - 仅在知识点编号和名称都能解析、数量一致且元素非空时建立配对；
  - 同步 `knowledge_id`、`knowledge_name`、`knowledge_ids` 与 `knowledge_points`；
  - 已是合法标量或合法结构的数据保持原有含义；
  - 无法解析、单边列表或数量不一致的数据继续保留阻断提示。
- **明确不包含：**
  - 修改题目、答案、评分步骤、分值、模型提示词、批次、重试或计费行为；
  - 猜测缺失知识点、自动补写业务内容、发起真实模型请求；
  - 修改真实 `user_data/` 或数据库 Schema；
  - 借本缺陷修复扩大 P2-20 的验收范围。
- **验收条件：**
  - 使用与 Q10/Q12 同形的单引号列表文本时，公开规范化入口生成正确配对，质量阻断消失；
  - 规范化前后答案内容和题目分值不变；
  - 畸形文本、单边列表和数量不一致仍被阻断；
  - 受影响测试和快速冒烟通过，真实数据与模型均未触碰。
- **风险等级：** 中。改动会影响生成配置的保存资格和已有草稿恢复，但不修改模型调用、答案或分值。

## 集中调查与根因

问题清单冻结为一个根因：`normalize_generated_config_schema` 会先把顶层知识点字段强制转成普通文本，而 `_normalize_question_knowledge_fields` 不识别其中的列表文本；随后质量检查把 `knowledge_name` 的方括号文本误报成“答案列表字符串”，导致本来可安全规范化的评分依据无法保存。

浏览器和只读副本证据表明：Q10/Q12 的异常仅在知识点元数据中；答案文件未出现同类列表文本，题目分值也不受影响。将两个知识点列表在内存中按位置配对后，阻断数归零，答案摘要和所有分值保持不变。

## 故障场景与预期

| 场景 | 预期结果 |
|---|---|
| 重复规范化 | 结果幂等，不重复知识点，不改变答案或分值。 |
| 同时操作 | 不新增共享状态或锁；继续使用现有配置保存锁。 |
| 中途退出 / 重新启动 | 已落盘草稿仍可由现有恢复入口重新规范化；不自动发布。 |
| 失败重试 | 不增加模型请求；不可安全解析的数据继续阻断。 |
| 取消 | 不适用；本地同步规范化不新增异步任务。 |
| 部分完成 | 只有编号与名称完整配对时才转换；否则整体保留原值并阻断。 |
| 数据缺失或冲突 | 单边列表、空元素、数量不一致或非法字面量不做猜测。 |

## 模块接口与测试策略

- TDD 公开 seam：现有 `normalize_generated_config_schema` 与 `collect_generated_config_quality_warnings`。
- 先增加真实同形的失败用例，验证知识点配对、阻断消失以及答案/分值不变；再补畸形与数量不一致的保守用例。
- 最小实现只位于知识点字段规范化边界，复用 Python 安全文字解析，不引入新的模型、存储或前端接口。
- 稳定候选冻结后，同一 SHA 进行一次需求符合性与代码质量并行复审；如存在阻塞意见，只统一修复一次并限定终审。
