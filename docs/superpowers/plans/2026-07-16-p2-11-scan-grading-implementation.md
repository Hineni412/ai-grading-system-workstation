## Objective

在不改变扫描匹配算法、评分算法、评分模式语义和生产入口的前提下，交付独立的 Vue“批改执行”工作区：教师可以分批上传整班答卷、冻结上传批次并运行扫描预检、处理低可信和异常卷、并列启动整卷或混合批改、安全暂停/继续/取消、只重试原模式下的失败答卷，并在刷新或进程重启后看到与持久记录一致的任务、阶段、计数和恢复建议。

## Confirmed Decisions

用户于 2026-07-16 逐项确认：

1. 新增独立“批改执行”页面，从工作台和考试配置进入；评分复核继续只负责批改后的人工复核。
2. 同一上传队列允许分多次添加文件，按内容去重；预检前可移除或清空，预检开始后冻结。
3. 未处理异常卷不阻塞整班批改；启动前必须展示正常批改数与跳过数并显式确认；异常卷保留供后续匹配和补批。
4. 暂停从同一批次断点恢复；取消终结本次任务，保留已完成结果，未完成答卷不算失败，后续需要新建任务。
5. 整卷与混合批改并列同等可见；每种模式各自提供“仅重试失败答卷”，默认且必须沿用原失败任务的模式。
6. TDD 只锁定三类公开 seam：页面操作、前后端契约与刷新恢复、安全和数据边界；不测试内部代码组织。

### 已确认补批规则

用户于 2026-07-17 确认：异常答卷后来匹配成功后的补批沿用本批次首次运行模式，只处理后来新匹配且从未进入批改运行的答卷；“补批新匹配答卷”与“仅重试失败项”保持两个独立动作；补批只在正常完成或部分失败后提供，已取消运行仍必须显式新建批次。

### 全部已知问题与根因分组

| 根因组 | 去重后的已知问题 | 一次性修复边界 |
|---|---|---|
| R1. Job 与领域账本缺少统一终态编排 | 取消请求与正常完成竞态会停在“取消中”；进程重启后取消请求可能永久悬空；恢复未先核对当前配置指纹，可能新建运行并重复批改 | 由会话工作区统一按关联 Job 终态、run 状态、控制记录和当前配置指纹投影动作；成功完成可以赢得未确认取消竞态；重启失败转为可恢复状态；恢复不匹配返回 409，不创建新 run |
| R2. 扫描预检没有当前批次所有权 | 活动预检期间可开始新批次，旧 Job 随后可能覆盖共享快照；浏览器关闭或进程重启后冻结批次无法安全重跑 | scan Job 创建、查询、重跑和发布都绑定 `scan_batch_id`；活动预检阻止新批次；发布前复核当前批次；服务器工作区投影当前预检 Job，failed/cancelled 后允许同一冻结批次重跑 |
| R3. Vue 只保存局部浏览器状态 | 批改 Job 轮询不刷新运行摘要；异常确认勾选未绑定上传/决定 revision，决定变化后旧确认仍有效 | 前端只以服务器工作区为恢复真相；扫描和批改 Job 轮询都在当前请求世代内刷新工作区；确认令牌绑定当前 `batch_id + upload_revision + decision_revision`，任一变化立即失效 |
| R4. 后续新匹配答卷没有独立补批语义 | 首次运行后保存的新 match 决定没有补批入口，若复用普通启动或失败重试会混淆范围 | 增加当前 run 专用“补批新匹配答卷”动作；沿用原模式，只接收当前预检中后来匹配且从未进入 run 的来源；取消态拒绝，完成/部分失败态才允许；不混入既有失败项 |

### 固定故障矩阵

- 批改运行：Job succeeded/failed/cancelled 与 run running/paused/completed/failed 的允许投影；取消写响应丢失与进程重启；配置指纹相同/变化；不得重复创建 run。
- 扫描预检：同批并发启动、活动时新批次、发布前批次变化、queued/running 重启失败、failed/cancelled 后重跑、旧快照保留。
- 前端恢复：扫描与批改轮询、刷新/关闭再开、跨 session/批次旧响应隔离、revision 改变后确认失效。
- 后续补批：新匹配 0/1/多份、已进入 run 的来源排除、失败项不混入、原模式保持、取消态拒绝、重复点击幂等。

### 收口规则

- 继续使用已确认的三类公开 seam：HTTP/API、Vue 用户流、真实浏览器 + 临时服务；不新增内部实现耦合断言。
- 四组根因按垂直切片完成 RED→GREEN，但在全部已知问题修完前不发起复审。
- 稳定候选只运行受影响回归、真实匿名浏览器、快速冒烟和真实两库指纹守卫；完整 pytest 留在 M2-01 里程碑门槛。
- 只进行一次最终 Spec / Standards 并行复审；仍有 Critical/Important 时停止，不在本任务内继续修改。
