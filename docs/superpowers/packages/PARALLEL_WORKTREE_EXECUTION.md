# 并行 Worktree 执行手册

本文只保存长期有效的并行、集成与清理规则。当前包状态和队列见 `EXECUTION_INDEX.md`；实际 worktree、分支和提交必须在每一波开始时现场核验，不得从本文推断。

## 1. 现场核验与数据红线

开始任何并行波次前：

1. 获取最新 `origin/main`，列出 worktree、分支、HEAD、领先/落后和工作树状态。
2. 分别检查源码状态与 `git status --short -- user_data`，不得把根目录真实数据脏状态带入功能提交。
3. 记录真实两库的大小、UTC 修改时间和 SHA-256；验证只在临时副本进行写操作。
4. 核对候选包在 Index 中的状态、Phase map 依赖、即时计划和交接块。
5. 发现未知提交、未知本地数据、依赖未进入 `origin/main`（或未进入 Index 声明的当前里程碑精确基线）或外部 reparse point 时停止。

真实 `user_data/` 不得被修改、删除、暂存、提交或 stash。任何真实数据操作都需要针对本次具体动作的单独授权。

## 2. 一个滚动功能通道加一个集成通道

普通开发默认采用低占用串行拓扑：

| 目录/通道 | 默认职责 | 生命周期 |
|---|---|---|
| 根目录 | 只保持本地 `main`，承载真实工作机数据 | 长期保留 |
| 滚动功能 worktree | 当前一个执行包的源码、测试、即时计划和独立短分支 | 当前包交给 integration 并安全释放后复用物理目录 |
| integration worktree | 当前里程碑逐包集成、冲突整理和组合门槛 | 当前里程碑内保留；合入主线后同步新主线或在无后续批次时清理 |

默认不同时占用两个功能 worktree。只有 Index 已明确记录并行收益、文件所有权、第二通道和精确基线，且真实数据风险受控时，才临时增加第二个功能通道；最多仍为两个功能通道加一个 integration 通道。

- 功能通道只实现一个正式包，拥有该包的源码、测试和即时计划。
- 复用的是物理 worktree，不是功能分支；每个执行包仍使用独立短分支。
- integration 通道只接收已经完成、验证并复核的提交链，解决共享入口与文档冲突并运行组合门槛。
- integration 不顺手修业务缺陷；发现问题退回原功能分支。
- 功能分支不直接 push 或合并 `main`，也不通过改共享状态文档宣称已经集成。

### 滚动复用门槛

滚动功能 worktree 只有同时满足以下条件，才可切换到下一包：

1. 上一包已经进入当前里程碑 integration，并完成逐包验证和 Index 所需记录。
2. 源码状态干净，`user_data/` 没有本地项，未新增 stash，且没有未知提交。
3. 已核对全部 junction、symlink 和 reparse point；不存在指向工作目录外部的链接。
4. 上一包短分支已由主线或 integration 保留完整交接证据，不会因切换目录丢失未交接历史。
5. 下一包新分支从 Index 记录的 `origin/main` 或当前里程碑已验证精确 SHA 创建；不得在上一包分支继续提交。

没有活动里程碑时，不为维持形式而保留空功能 worktree 或空 integration worktree。

## 3. 三包里程碑与依赖基线

1. 一个滚动功能 worktree 同一时间只承载一个执行包和一个对应短分支。
2. 普通开发每批固定 3 个相关执行包。数据库迁移、核心状态机、生产切换、正式用户验收、删除等高风险包可以单独成批，不为凑数搭配无关任务。
3. 第 1 包从最新 `origin/main` 创建；第 2、3 包必须各自创建新功能分支，但可以在安全释放后的同一滚动功能 worktree 中，从当前里程碑 integration 已完成逐包验证的精确 SHA 创建，不在旧功能分支继续叠包。
4. 里程碑的编号、固定顺序、起始主线 SHA、integration 分支和当前已验证 SHA 必须先由 Index 唯一声明。未进入该声明的本地 `verified` 或其他未合并分支不能满足依赖。
5. 使用里程碑基线的即时计划必须在交接块外声明不可变的 `交接基线` 完整 SHA；未声明时仍只接受 `origin/main`。调度方先从 integration 现场解析 Index 记录的“当前已验证 SHA”，再以 `--expected-handoff-base <SHA>` 作为独立可信输入调用 `tools/handoff_status.py`；验证器要求计划值与可信值精确相同且为当前分支祖先。缺少可信值时拒绝里程碑交接，不能只凭计划自证。
6. 每包开工前根据当时源码生成即时实现计划，并在首次源码修改前建立交接块。包的稳定边界来自 Phase map；动态状态、里程碑组成和领取顺序只来自 Index。
7. 若两个候选包存在共享迁移、状态机或主要业务文件，改为串行，或先由 integration 明确拆分文件所有权。
8. 某包失败时退回其功能分支修复，保留此前已经验证的包；同一包第二次仍有 Critical/Important 时停止并汇报。第 3 包确实受阻时，允许前 2 包作为“部分里程碑”完成一次完整门槛后收口，不把失败包带入 PR。

## 4. 共享文件和冲突所有权

| 共享范围 | 规则 |
|---|---|
| `AGENTS.md`、`ARCHITECTURE.md`、`EXECUTION_INDEX.md` | 功能分支只记录包专属事实；最终状态、数量和下一动作由 integration 统一整理 |
| `backend/api/app.py`、router/schema `__init__.py` | 功能分支只做最小注册；integration 合并时同时保留各包契约 |
| OpenAPI 与全局测试清单 | 包内新增契约测试；全局快照和组合证据由 integration 更新 |
| Job handler 注册和 Job schemas | 多个 Job 包默认串行，不在不同 worktree 同时重排注册逻辑 |
| `llm_client.py`、`backend/llm/`、AI tagging 链 | LLM Gateway、调用迁移和 tagging 包默认串行，除非文件所有权已明确分离 |
| `question_bank/services/` | 题库写入、导入和 Training 包开工前重查重叠文件；重叠即串行 |
| 依赖锁、发布清单和启动入口 | 由对应工程基础或切换包独占；升级必须有独立包边界 |
| 数据库迁移 | 不并行创建相邻迁移号；integration 核对顺序并在副本预演 |

## 5. 功能包完成门槛

功能包只有同时满足以下条件才可交给 integration：

1. 起点与依赖核验通过，任务范围没有扩散到其他包。
2. 新行为有 RED → GREEN 证据，没有为测试改写业务口径。
3. 包内聚焦测试、相关回归和 `tools/smoke_check.py --skip-tests` 通过。
4. 高风险包完成指定级别复核，Critical/Important 为零。
5. `git diff --check` 通过，提交不含真实数据、临时数据库、缓存、构建噪声、真实导出或密钥。
6. 技术交接保留修改范围、验证证据、风险、回退和建议合并顺序；面向用户的摘要按“结果、影响、是否需要用户操作、下一选择”组织，并把必要术语解释成用户可理解的语言。
7. `tools/handoff_status.py` 验证通过，最终为 `verified_pending_integration`；功能 SHA 与只改即时计划的交接提交关系正确。

### 分层测试与证据复用

1. 开发反馈从当前测试或单个 `-k` 用例开始，行为稳定后扩大到包内聚焦测试和受影响回归；不得把全量 pytest 当作每次修改、复审或提交后的默认反馈命令。
2. 独立复审修复只重跑覆盖该问题和实际影响面的测试。纯文档、交接状态更新、提交整理、PR 合并后的主线同步不单独触发全量测试。
3. 功能分支交接以包内聚焦测试、相关回归和 `tools/smoke_check.py --skip-tests` 为门槛；integration 每合入一个包运行该包聚焦回归和受影响的 API/前端命令，批次末只运行一次完整门槛。包含前端时统一运行 `npm run verify`，已经由该命令构建成功的同一 SHA 再运行 `*:prepared` 浏览器命令，不重复构建或重复类型检查。
4. 完整测试结果仅在代码 SHA、依赖基线和测试配置完全相同，且验证后没有实质代码变化时复用；文档提交不得改变被验证代码 SHA 的判定范围，交接必须记录实际被测功能提交。
5. 以下情况必须按影响和风险增加全量测试：上次全量后发生实质代码变化；合并冲突后手工改代码；公共基础设施或依赖锁变化；数据库 Schema 或核心状态机变化；跨域共享入口变化；测试失败或出现不稳定；最终候选 SHA 与已验证 SHA 不一致；执行包定义明确要求专项全量门禁。
6. 删除、破坏性迁移和其他高风险包的专项全量测试、数据库副本预演与真实数据指纹守卫继续执行，不得用证据复用规则绕过。
7. 测试失败时先修复并重跑失败用例及受影响回归；最终候选仍须在规定的波次末完整门禁通过，禁止用多次无代码变化的全量重跑替代根因分析。
8. 完整 Python 测试的并行化分两批验证：第一个里程碑在同一 SHA 上各运行一次串行完整门槛与 `tools/smoke_check.py --parallel-tests --pytest-workers 2`，比较数量、结果、耗时和慢测试；第二个里程碑先以 2 个进程运行，出现不稳定立即退回串行。连续两个里程碑稳定后才可把 2 个进程改为默认；数据库、端口、进程及其他隔离清单中的测试始终留在串行车道。
9. P3-01 建立覆盖率和耗时基线前，不按数量合并或删除测试；合并或删除测试必须用业务覆盖对照证明没有降低保护范围。

## 6. 集成顺序和验证

1. integration 从最新共同基线开始，确认没有未知改动或独有业务提交。
2. 一次只接收一个正式包的完整提交链，先核对交接证据，再合入依赖更基础、共享面更小的包。
3. 每次合入立即运行该包聚焦回归和受影响的 API/前端命令。
4. 当前里程碑全部合入后只运行一次完整 `tools/smoke_check.py`；处于并行试点时按上方规定在同一 SHA 做一次对照。存在前端时运行一次 `npm run verify`，再按需要复用已构建产物执行浏览器检查。需要额外全量测试时必须符合上方风险触发条件并记录原因。
5. 比较验证前后真实两库大小、修改时间和 SHA-256；未经本次授权的任何变化都是阻塞。
6. 最后统一更新架构事实、Index 状态和必要的包证据；测试流水数字不复制到长期入口。
7. 每包受影响门槛通过后，当前里程碑的下一包可以从该 integration 精确 SHA 创建；只有里程碑完整门槛通过并进入主线后，下一里程碑才能开始。

linked worktree 不应复制根目录便携运行时。后端验证以目标 worktree 为工作目录调用仓库根目录运行时；前端工具链每次通过 workspace dependencies 重新探测，不把本机绝对路径写进项目配置。物理目录复用后仍必须重新核对运行时和依赖入口，不继承上一包的临时构建状态作为验证证据。

## 7. 必须暂停的情况

- 依赖包尚未进入共同基线。
- 两个实现包需要同时修改同一业务服务、迁移或状态机。
- 测试需要真实数据、真实密钥、真实模型调用或不可逆文件操作，但没有本次明确授权。
- API 字段、评分规则、标签语义或状态含义与包定义不一致。
- 同一包连续两次修复失败，或复核仍有 Critical/Important。
- 合入后完整冒烟、前端构建或数据库指纹守卫失败。
- 样板页尚未获得要求的用户确认，却准备扩散复杂页面迁移。
- 准备开始 P2-09 至 P2-22 时，最新 `origin/main` 的 `EXECUTION_INDEX.md` 必须明确记录 Phase 2 前端来源重校准门槛通过，且匹配的版本化用户验收证据必须已进入同一共同基线；任一缺失都必须暂停。

暂停后保留证据并回到原包或用户决策，不通过扩大范围绕过门槛。

## 8. Main 同步与安全清理

1. 功能分支分别完成提交、验证、复核和交接。
2. integration 更新到最新 `origin/main` 后一次合入一个包，并逐包回归。
3. 里程碑的 3 个包（或已明确记录的 2 包部分里程碑）进入 integration 后运行一次完整门槛与真实两库指纹守卫。
4. 推送 integration 分支并创建以 GitHub `main` 为目标的 PR；检查通过后合并，禁止直接 push `main`。
5. `git fetch --prune` 后，将本地 `main` 和活动 worktree 快进到 `origin/main`；根目录保持本地 `main`。
6. 删除已合并的远端 integration 临时分支；有下一里程碑时，本地 integration worktree 重新跟踪 `origin/main` 后复用；没有已声明的下一里程碑时可以按安全清理规则移除，下一批再创建。
7. 只有 `git branch --merged origin/main` 能证明候选分支已被主线包含。未合并历史默认保留，丢弃必须单独获得用户授权。
8. 删除或重新分配 linked worktree 前分别核对源码、`user_data/` 和所有 junction/symlink/reparse point。存在本地数据、独有提交或指向外部的链接时停止。
9. 通过核验后，只能从仓库根目录执行 `git worktree remove <verified-path>` 和 `git worktree prune`；禁止手工递归删除目录。
10. 清理前后再次比较真实数据状态与两库指纹，任何变化立即停止。

用户启动执行包即授权标准功能提交和 integration PR 流程；直接 push `main`、force push、真实数据操作和未合并历史丢弃仍需单独明确授权。
