## P3.5 例外

P3.5 是 Phase 3 完成后的用户主导改进阶段，不是正式执行包体系。

- 固定使用长期分支 `codex/p3.5-interactive-refinement`。
- 用户逐批提出真实需求，Codex 调查后直接修改真实应用。
- 不建立样板页、执行包、即时实现计划、交接块、integration 分支或里程碑。
- 不运行自动测试，不启动代码复审，不用版本化验收清单代替用户交流。
- 可以按需运行或构建应用供用户查看，但不把命令结果当作流程门槛。
- 用户满意后冻结范围，只统一精简一次；随后由用户最终人工确认。
- 最终人工确认前不得 push、创建 PR、合并或同步 `main`。

P3.5 期间只在 Index 记录当前状态、工作约定、待讨论事项和下一动作，不记录每批命令、测试数字、提交流水或复审过程。

## 安全底线

以下动作不因 P3.5 处于直接协作阶段而获得授权：

1. 读取、复制、修改、迁移或删除真实 `user_data/`。
2. 调用真实模型、使用真实密钥或进行可能产生费用的网络请求与重试。
3. 数据库迁移、批量覆盖、永久删除或其他不可逆操作。
4. push、PR、合并、同步主线或丢弃未合并历史。

每次具体动作都必须单独获得用户明确授权。真实数据永远不得暂存、提交或 stash；获得写入授权时仍须先确认精确目标、备份和回退。

## 未来正式 Phase 的通用短规则

只有用户明确结束或暂停 P3.5，并在 Index 中恢复某个正式 Phase 后，才使用以下流程：

1. 先根据当时源码和用户目标冻结范围、明确不包含内容、验收条件和风险。
2. 只有确有多个可独立交付、需要依赖管理的工作项时才建立执行包；不为形式拆包。
3. 每个正式工作项使用短分支。多个工作项确有组合验证价值时才建立 integration；否则直接通过单一 PR 合入。
4. 自动测试、代码复审、数据库副本预演和用户验收按风险与用户决定写进当次范围，不从历史包机械复制。
5. 真实数据、费用、迁移和不可逆操作仍逐次授权。
6. 候选完成后通过 PR 合入 `main`，同步当前架构和 Index；过程证据留在 Git/PR，不扩写长期入口。

P3.5 的流程例外不能作为未来正式 Phase 跳过其已冻结门槛的依据。

## 安全停机

出现以下任一情况时停止当前实现并请求用户决定：

- 需求会改变评分规则、数据语义、状态含义、安全或恢复结果。
- 需要真实数据、真实模型费用、迁移或不可逆操作。
- 当前批次将扩张到用户没有提出的相邻功能或 Phase 4。
- 无法确定目标文件、数据对象、费用上限或回退方式。
