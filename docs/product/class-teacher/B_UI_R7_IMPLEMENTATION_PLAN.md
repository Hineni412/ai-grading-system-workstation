# B-UI-R7 班主任对话首页与事务交接实施计划

> 状态：`design_frozen_pending_checkpoint_sync`
>
> 业务线：B（班主任工作台）
>
> 依赖：共同地基 `TW-F1` 及 `docs/product/teacher-workspaces/AI_TASK_AND_HANDOFF_CONTRACT.md`
>
> 权威复核位置：`codex/teacher-workspaces-design-freeze` 的完整文档候选。B 分支中的同名文件在共同文档检查点经用户授权提交并通过 Git 同步前只是工作稿，不得据此开始编码。
>
> 本文记录用户查看原型后确认的新一轮方向。它替代旧 B-UI-R1—R6 中与默认首页、单次输入、统一跳事务页、PIN/隐私闸门、匿名发送预览、自动重试和“我班名单整体替换”相冲突的目标描述；旧文档继续作为历史实现与复用证据。

## 1. 冻结边界

### 1.1 目标

把班主任首页从“一句话输入后得到一份事务草稿”升级为真正的日常工作入口：

1. 教师可以持续与 AI 对话，学生、班级、活动和学校事务都能直接说；
2. AI 必要时追问，把日常高频事务归入六个业务语义域；
3. 六域最终复用登记型、计划／日历型、SOP 型三种处理样式；
4. AI 形成草稿后自动打开相应页面并预填，但不自动保存、外发、惩戒、认定或结案；
5. 学生页成为独立补录资料与近期状态的工作面；
6. 班主任选择“我的班主任班级”，一直沿用到手动更改，并与左侧学生管理共用学生来源；
7. 模型调用接入共同 AI Task，可离页恢复、零自动重试。

### 1.2 包含

- A 型对话首页、会话历史、追问和交接卡；
- 六域分类、三样式映射、多事务拆分和解释；
- 可恢复 Handoff、route-state 和草稿引用；
- 登记型、计划／日历型、SOP 型页面 Adapter；
- 班主任班级偏好与现有学生管理名册接入；
- B 的共同 AI Task Adapter；
- 移除旧匿名化、发送预览、额外 PIN/解锁和模型自动重试路径；
- 受影响的 B API、迁移、测试和说明文档。

### 1.3 明确不包含

- 不建立复杂的学生成员权限、自动剔除或按场景逐层授权；
- 更换班主任班级时不自动删除学生、档案、事务或历史关联；
- 本轮不重做全局学生管理的导入、永久删除、成绩关联和阅卷业务；
- 不允许 AI 自动写正式档案、创建正式日历、发送消息、作诊断、作欺凌认定、决定惩戒或自动结案；
- 不在 B 分支修改公共 JobManager、共同任务抽屉、全局导航或 A/P4；
- 不调用真实模型，不读取或写入真实学生数据，不执行真实迁移或服务重启。

### 1.4 验收条件

- 默认首页不是学生列表，也不是只服务学生事务的页面；
- 一段对话能持续追问，并在刷新后恢复消息、任务和交接；
- 六个语义域的典型高频事务均有可走通的三样式落点；
- “补录学生近期状态”进入登记草稿，“黑板报两周后检查”进入计划／日历草稿，“两个学生发生冲突”进入 SOP 草稿；
- 模型失败时保留教师原文，可手动选三种样式继续，不出现死路；
- 自动打开页面不等于自动保存，正式动作都需要教师确认；
- 无 PIN、无隐私解锁、无匿名化或逐字发送确认；
- 重复、并发、取消、离页、重启和结果不明不会造成重复模型调用或重复业务写入。

### 1.5 风险等级

`中高`。本轮涉及未成年人工作信息、模型任务、会话持久化和跨页面草稿，但不授予 AI 正式处置权，也不在文档阶段处理真实数据。

## 2. 现状与替代关系

### 2.1 可直接复用

- `QuickWorkCapture` 已有发送、追问、查询原调用和失败状态的交互基础；
- `home_intake_drafts` 已有可恢复、可留版本的集中草稿；
- `IntakeDraftWorkspace` 已有“草稿—局部调整—教师确认”的事务驾驶舱；
- 学生目录、支持记录、日历、普通事务和 SOP 已有业务页面；
- 现有六套 SOP 模板可作为流程资源，但不再等同于用户看到的六个事务分类；
- 全局学生管理已经保存姓名、学号和班级，B 已有只读 roster source Adapter。

### 2.2 必须替代

- 当前首页是单个文本框，追问依靠拼接原文，没有持久消息序列；
- 当前成功结果通常统一进入事务页，无法准确落到学生登记或计划页；
- 当前“学生支持”最终仍可能创建普通事务，缺少真正的学生记录 adopt 语义；
- route-state 只记栏目，缺少 conversation、turn、work_item、draft 和目标 revision；
- 部分普通事务后端输出与前端完整事务解码器不一致，存在真实解码失败路径；
- B 仍有同步模型直调和内部自动重试；
- 旧匿名化、目的地逐字确认和敏感解锁 UI 与本轮用户决定冲突；
- 当前“替换我班名单”会把旧名单自动转历史；本轮改为持久化班主任班级偏好，不再自动删减成员。

## 3. 班主任事务领域模型

### 3.1 六个业务语义域

| domain | 中文名称 | 典型高频事务 |
| --- | --- | --- |
| `student_growth` | 学生资料与成长记录 | 补录基本情况、课堂观察、谈话记录、阶段变化、表扬与跟进结果 |
| `student_support` | 学生支持与家校沟通 | 个别关怀、家长沟通、家访准备、请假后跟进、支持计划 |
| `conflict_safety` | 冲突、安全与异常事件 | 学生争执、受伤、疑似欺凌线索、失联或其他需要学校流程的异常 |
| `class_operations` | 班级日常管理 | 值日、卫生、座位、作业收缴、通知回执、班会、常规检查 |
| `activities_culture` | 活动与班级文化 | 黑板报、运动会、科技节、班级展示、评优、集体活动复盘 |
| `school_coordination` | 学校协同与报送 | 年级任务、材料报送、数据收集、部门协同、会议要求和规定流程 |

六域是 AI 理解和统计的语义层，不要求教师发送前选择，也不直接决定页面数量。

### 3.2 三种处理样式

| handling_mode | 解决的问题 | 主要构成 | 正式写入点 |
| --- | --- | --- | --- |
| `record` | “把已经发生或已确认的内容记下来” | 对象、时间、来源、事实/转述/判断、状态、后续复查 | 学生记录或事务记录，教师确认后写入 |
| `plan_calendar` | “把未来要做的事拆开并放到时间上” | 目标、截止、行动、依赖、负责人、提醒和完成结果 | 计划/日历，教师确认后创建 |
| `sop` | “按安全或学校流程处理一件连续事务” | 即时安全、事实采集、角色、必做步骤、分支、交接、复查和结案条件 | 德育事务，教师确认后创建 |

三种样式不是三个互相封闭的业务库。一个事务可以有一个主要样式和若干后续样式，例如先走冲突 SOP，再补学生记录和复查日历。

### 3.3 六域到三样式的主映射

| 语义域 | 主要样式 | 常见次样式 | 说明 |
| --- | --- | --- | --- |
| 学生资料与成长记录 | 登记型 | 计划／日历型 | 记录事实后可安排复查 |
| 学生支持与家校沟通 | 按意图选择登记或计划 | SOP 型 | 已发生沟通先登记；未来联系走计划；安全风险走 SOP |
| 冲突、安全与异常事件 | SOP 型 | 登记型、计划／日历型 | 先保证安全和流程，再记录、复查 |
| 班级日常管理 | 计划／日历型 | 登记型 | 常规事项拆解、提醒和结果记录 |
| 活动与班级文化 | 计划／日历型 | 登记型 | 活动筹备、节点检查和活动复盘 |
| 学校协同与报送 | 按意图选择计划、登记或 SOP | — | 有截止的报送走计划；已完成的交接登记；规定流程走 SOP |

## 4. AI 分诊结果契约

班主任 Adapter 校验后的结果至少包含：

```json
{
  "contract_version": "class_teacher_triage.v1",
  "assistant_message": "给教师的简洁说明",
  "clarification_questions": [],
  "work_items": [
    {
      "work_item_id": "opaque-id",
      "domain": "activities_culture",
      "primary_mode": "plan_calendar",
      "secondary_modes": ["record"],
      "intent": "plan",
      "reason_summary": "有明确检查期限且包含多个准备步骤",
      "subject_refs": [],
      "time_facts": [],
      "safety_level": "normal",
      "missing_fields": [],
      "draft_ref": {"id": "opaque-id", "revision": "1"},
      "handoff_key": "class_teacher.plan.calendar"
    }
  ]
}
```

### 4.1 多事务输入

教师可以在一条消息里说多个互不相干的事项。AI 可以拆成多个 `work_item`；每个 work_item 产生独立 Handoff，首页以紧凑清单展示并逐项打开、采用或丢弃。AI Task 只聚合显示“已处理 N/M”，不会因第一项采用就把整轮标为已保存。系统不自动连续打开多个页面，也不把多个正式对象捆成一次不可拆写入。

### 4.2 需要追问

只有缺少会阻止形成安全、有用草稿的信息时才追问 1—3 项。追问不重复已知内容，不强索姓名、电话、住址等与当前草稿无关的信息。

### 4.3 无法分类

- 模型结果不满足 contract 时进入 `invalid_result`，不伪造本地 AI 结论；
- 页面保留教师原文和会话；
- 教师可直接选择“登记／计划／SOP”继续，系统只把原文作为未确认草稿，不编造步骤；
- 这条手动路径不产生第二次模型调用。

## 5. A 型班主任首页

### 5.1 首页职责

首页只承担：

1. 说清一件事并与 AI 继续对话；
2. 看今天和近期真正需要处理的少量节点；
3. 从 AI 草稿进入正确工作页；
4. 回到未完成会话或草稿。

学生列表、全部日历、完整事务台账和长 SOP 不在首页展开。

### 5.2 桌面布局

```text
┌ 我的班主任班级／新对话／最近会话／任务抽屉 ─────────────────┐
│ 对话案头（主要区域，约 60%—68%）      │ 今日与接下来（约 32%—40%） │
│ 消息、追问、AI说明、交接卡             │ 待处理节点、未完成草稿       │
├─────────────────────────────────────────────────────────┤
│ 六个业务语义域：一条紧凑覆盖带，可点击看示例，不要求先选择    │
└─────────────────────────────────────────────────────────┘
```

- 不把六域做成六个等高大卡片；
- 不默认显示全班学生头像或名单；
- 右栏只显示有限数量且确实有下一动作的事项；
- 历史会话、全部任务和全部草稿进入抽屉或独立列表；
- 输入框始终贴近最近消息，但不遮挡交接卡。

### 5.3 对话消息

消息类型：教师消息、AI 普通回复、补问、任务状态、交接卡、失败与手动继续。AI 回复必须说明“我把它整理为什么、为什么适合这个处理方式、还缺什么”，不展示内部 prompt 或调试 JSON。

### 5.4 会话状态

`collecting → ai_running → needs_input → handoff_ready → draft_opened → teacher_confirmed`

旁支为 `failed/manual_routing/abandoned`。AI Task 状态另由共同契约管理；一个 Conversation Turn 绑定一个 operation，教师补充回答会产生新的 Turn 和新的 operation。

### 5.5 发送行为

- 不做 PIN、解锁、匿名化或逐字发送确认；
- 教师按“发送”即冻结本 Turn 并创建共同 AI Task；
- 发送过程中可以继续浏览其他页面；
- 任务完成后在首页和任务抽屉同时出现安全通知；
- 模型目的地由全局配置决定，页面显示安全名称，不要求每轮再确认；
- 结果不明时只能查询原任务或放弃，不自动重发。

## 6. 页面交接

### 6.1 Handoff 路由状态

URL 只保存不透明 ID：`view/conversation/turn/work_item/handoff`。姓名、教师原文、草稿正文和 AI 输出不进入 URL、localStorage 或公共任务 API。

### 6.2 自动打开的边界

- AI 结果校验通过且只有一个主要 work_item 时，可以自动打开目标草稿页；
- 有多个 work_item、重名学生、缺目标对象或需要教师选择模板时，先在首页展示交接清单；
- 自动打开只读取 draft_ref 并预填；
- 正式保存按钮必须在目标页面，由教师点击；
- 目标 revision 变化时 Handoff 标 stale，保留草稿并要求重新选择目标。
- `handling_mode` 与 destination_key 分开：学生成长记录进入 `class_teacher.student.record`；活动复盘、学校交接和一般事务登记进入 `class_teacher.affair.record`；计划和 SOP 分别进入其允许目标。

### 6.3 返回

目标页面提供“返回这次对话”，恢复原 Conversation、Turn 和 work_item 焦点。教师可以在原会话中补充情况，形成新版本或新的后续工作项。

## 7. 登记型页面

### 7.1 适用

- 学生近期状态、课堂观察、谈话与沟通结果；
- 活动或事务复盘；
- 学校交接完成事实；
- 需要保留来源、时间和复查的记录。

### 7.2 页面结构

- 左侧：已选学生/事务、近期相关记录和来源；
- 中间：事实、转述、教师判断和 AI 草稿分区；
- 右侧：缺失项、冲突、复查建议和教师决定；
- 底部：一个“确认保存记录”主动作。

AI 预填不能把转述升级为事实，也不能替教师作诊断。教师可以逐字段采纳、修改或清空。

### 7.3 学生匹配

- 姓名唯一匹配时可以预选；
- 重名、无匹配或多个班级同名时必须让教师选择；
- 没有选中学生仍可保留会话草稿，但不能保存为正式学生记录；
- 选择学生后只绑定不透明 subject_id，不把姓名写入共同 Handoff。

## 8. 计划／日历型页面

### 8.1 适用

班级日常、活动筹备、学校报送、家校跟进和其他有截止、依赖或提醒的工作。

### 8.2 页面结构

- 左侧：事务简报、目标、截止与约束；
- 中间：横向日期/阶段流程，展示行动、等待、决定和依赖；
- 右侧：当前步骤、AI 调整、冲突和负责人；
- 底部：一个“确认加入计划／日历”主动作。

### 8.3 日期

- 明确日期和相对日期先本机解析，显示解释后的实际日期；
- “两周后检查黑板报”可以生成准备、初稿、自查、完善和检查节点；
- AI 提出的日期必须可编辑，日期冲突不能静默选一个；
- 无明确日期时可以生成待定计划，但进入正式日历前由教师补充或确认；
- 同一行动在首页、计划页和日历中是同一业务身份，不复制三份。

## 9. SOP 型页面

### 9.1 适用

学生冲突、受伤、疑似欺凌线索、需要学校角色介入的安全异常，以及学校规定的连续流程。

### 9.2 页面结构

- 顶部：即时安全提醒和当前处理状态；
- 左侧：事务简报、参与人和已知/未知事实；
- 中间：按阶段排列的 SOP 流程；
- 右侧：当前步骤、证据来源、AI 调整和学校交接；
- 底部：一个与当前步骤对应的教师决定。

### 9.3 安全与教师权

- 冲突或受伤优先显示确保人身安全、分开当事人、记录直接事实和通知有权角色等步骤；
- AI 可以完整提出建议，但页面标明“AI 建议，待教师判断”；
- AI 不能把线索变成欺凌认定，不能作医学或心理诊断，不能决定停课、停学等惩戒；
- 结案必须由教师或有权人员确认；
- 安全必做步骤可以调整负责人、时间和做法，但不能被模型自动删除。

## 10. 我的班主任班级与学生管理

### 10.1 单一学生来源

左侧“学生管理”继续是学生姓名、学号和班级的主来源。B 通过只读 Adapter 使用这些学生身份，不复制一套需要分别维护的基础名册。

### 10.2 班主任班级偏好

- 教师从现有班级列表选择一个 `homeroom_class`；
- 选择保存在 B 的普通偏好中，一直沿用到教师手动更改；
- 首页、学生页、对话姓名匹配和事务参与人默认使用该班；
- 没有选择时，首页仍可处理非学生事务；需要学生时引导一次选择；
- 更改选择只改变默认筛选，不删除学生、不把旧班学生自动转历史、不改已有记录或事务；
- 偶发多一名学生不触发复杂权限判断或自动剔除，教师可在学生管理中按现有方式维护。

### 10.3 B 学生页

- 默认筛选当前 homeroom_class；
- 提供搜索、最近状态、待跟进和补录入口；
- 可以查看与旧班级或历史学生关联的已有记录，但不混入当前班默认列表；
- 从对话交接进入时定位学生和登记草稿；
- 本轮不改变全局学生永久删除流程，也不新增自动删除。

## 11. ClassTeacherIntake 深 Module

建议由一个 B 专属深 Module 统一隐藏会话、分诊和交接复杂度：

```text
backend/class_teacher/intake/
  conversations.py
  triage_contract.py
  ai_task_adapter.py
  handoffs.py
  record_adapter.py
  plan_adapter.py
  sop_adapter.py
```

它向页面提供小 Interface：

```text
start_conversation(context) -> Conversation
append_turn(conversation_id, revision, message, operation_id) -> Turn
get_conversation(conversation_id) -> ConversationView
open_handoff(handoff_id, target_revision) -> DraftView
adopt_handoff(handoff_id, draft_revision, target_revision) -> Receipt
```

Module 负责：消息版本、六域分诊、三样式 Adapter、草稿与 Handoff。页面只调用 B 的 `adopt_handoff` API；该 API 内部委托共同 adopt 协调器，并由 B Adapter 完成领域写入，不存在第二条页面采用 Seam。共同 AI Task 负责：发送尝试证据、幂等、取消、重启和 Handoff 聚合。页面不得直接拼接旧 `affair/student_support` 临时内存对象。

## 12. B 的共同 AI Task Adapter

### 12.1 task_kind

首版使用：

- `class_teacher.intake_triage`
- `class_teacher.draft_revision`

同一次 triage 可以返回多个 work_item，不为每个 work_item 重复调用模型。教师对某个草稿提出 AI 调整时创建新的 `draft_revision` operation。

### 12.2 输入与存储

- B 自身存储完整 Conversation 与 Turn；
- Adapter 根据 conversation revision 构造模型输入；
- 不做匿名替换或逐字预览；
- 共同任务表只保存 conversation/turn 的不透明引用、指纹、由 registry 派生的固定安全标题和发送尝试证据；
- 模型原文和 triage proposal 保存在 B 自身数据区；
- 普通日志、公共 API 和 localStorage 不返回对话正文。
- 统一 Gateway 对 B 工作台强制使用 `metadata_only` 诊断；共享 AI 调用记录不得保存 prompt、请求、响应或姓名，Adapter 无权关闭这一模式。
- 每个 Handoff 使用共同 Module 分配的稳定 adoption_id；B Adapter 在目标业务库同一事务写正式对象和 Adoption Receipt。一个 Handoff 不跨两个 B 数据库，需要学生记录和日历时拆成两个 Handoff。

### 12.3 零自动重试

把 `configured_model` 的自动重试关闭。查询 task 状态可以网络退避；模型调用失败、invalid_result 或 result_unknown 都不会隐式产生第二次发送尝试。教师显式“重新整理”会建立新 Turn 或新 revision operation。发送边界前崩溃且尝试数仍为 0 时，可以按共同契约显式继续同一 operation；一旦标为 `may_have_started`，页面只能说明“可能已发送”并查询或放弃。

## 14. 故障场景

| 场景 | 预期结果 |
| --- | --- |
| 重复发送同一 Turn | 同 operation 最多保留一次发送尝试，返回同 Task |
| 多窗口同时回复 | conversation revision 冲突，后提交者先刷新，不串消息 |
| 一条消息多件事 | 拆成多个 work_item，逐项打开和确认，不捆绑正式写入 |
| 模型要求补充 | 保存 needs_input；教师回复形成新 Turn，不覆盖原文 |
| 模型失败或未配置 | 保留原文，手动选三样式继续，不伪造 AI 步骤 |
| 返回未知 domain/mode/URL | contract 拒绝，进入 invalid_result；任意 URL 不跳转 |
| 姓名无匹配或重名 | 草稿可保留；正式学生记录前要求教师选 subject_id |
| 切换班主任班级 | 新默认立即生效；旧学生和历史记录不删除、不转历史 |
| 离页或刷新 | 从 conversation/turn/handoff 恢复原消息、任务和草稿 |
| 应用重启 | dispatch 后无结果进入 result_unknown，不自动重发 |
| 发送后取消 | 停止本地后续；结果若返回先保存为未采纳，不谎报已撤回 |
| Handoff 保存失败 | 模型结果保留，只重试本地草稿/交接，不再次调用模型 |
| 一个 Handoff 已写正式对象但公共状态未更新 | B 领域 Receipt 与正式对象同事务保存；重放返回同一对象，不重复创建，其余 Handoff 状态不受影响 |
| 目标在交接后变化 | Handoff stale，不覆盖新 revision；教师重新选目标 |
| 安全事件信息不足 | 先显示安全优先提醒并追问最少事实；不自动认定或结案 |
| 正式写入部分失败 | 已写主对象不重复创建；次要日历/关联可单独恢复 |

## 16. 人工验收脚本

1. 未选择班主任班级时打开首页，确认仍可处理“学校周五交材料”等非学生事务；
2. 选择一个合成班级，刷新和重进后仍保持；
3. 发送“补录某同学近期状态”，必要时选择同名学生，进入登记草稿；
4. 返回原对话补充“月底提醒我复查”，进入计划草稿；
5. 新对话发送“黑板报两周后检查”，检查倒排步骤和日历日期；
6. 新对话发送“两名学生发生冲突”，检查安全优先 SOP、事实/转述分区和学校交接；
7. 在每个目标页面不点最终确认，确认正式库没有新增业务对象；
8. 模拟模型失败，使用手动三样式入口继续；
9. 模拟结果不明，确认只能查询原任务，不会再次调用；
10. 更换班主任班级，确认旧班学生记录仍在，系统没有自动删除或转历史；
11. 检查任务抽屉、URL、localStorage 和普通日志不显示合成姓名与对话正文。
