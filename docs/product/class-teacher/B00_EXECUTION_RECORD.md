## 2. 集中调查

### 调查范围

- 当前执行索引、三路并行规则、B 产品设计、详细实施计划和国家 SOP 基线；

- 当前便携 Python/SQLite/加密依赖能力；
- 根目录和现有 worktree 状态。

### 去重后的根因组

1. **保留责任混淆**：学校正式档案和教师个人工作副本不能使用同一套长期保留规则；
2. **角色与认定权混淆**：班主任负责发现、制止、记录和报告，不负责独自认定欺凌、心理诊断或学校级惩戒；
3. **页面密码不等于加密**：当前没有 SQLCipher，必须冻结可在便携环境落地的认证加密方案；
4. **普通基础设施会扩散敏感数据**：备份、日志、缓存、模型和恢复暂存都必须显式隔离；
5. **紧急流程不能依赖应用**：救助、制止和法定报告必须能绕过表单、AI和校内逐级等待。

### 故障场景

已覆盖重复操作、同时操作、中途退出、重新启动、失败重试、取消、部分完成、数据缺失和身份冲突；详见 [安全、加密、威胁与恢复规格](../../security/class-teacher/B00_SECURITY_AND_THREAT_MODEL.md) 第 5 节。

## 8. Worktree 数据安全纠正

最终检查发现仓库历史仍跟踪部分 `user_data` 文件，因此创建 B00 worktree 时 Git 自动检出了一份副本。这与“三路 worktree 不包含真实 `user_data` 副本”的规则冲突。

处理过程：

1. 只检查目录属性、跟踪状态和文件名，没有打开数据库、图片、文档或业务 JSON 内容；
2. 确认 B00 worktree 的 `user_data` 没有任何修改；
3. 使用该 worktree 独立的 sparse-checkout 排除整个 `user_data/`；
4. 核对 B00 worktree 中该目录已不存在；
5. 根目录原始数据、Git 历史和 B00 文档修改均未改变。

这是工作区安全纠正，不授权清理根目录或修改仓库历史中已有的数据文件。仓库仍跟踪 `user_data` 属于修改前已存在的问题，应单独立项评估，不能在 B00 中擅自修复。
